秸秆烟雾检测 v5 训练线 · 三条部署线路评估报告

v4 训练完成后的部署形态决策评审稿
编制：技术评估 ｜ 日期：2026-08-29 ｜ 依据：v4 训练回归实测 + 生产引擎与训练数据盘点

一、背景

v5 训练线的目标，是提升真实烟雾（特别是远山零星小烟、桥下烟柱等司空 2 无人机新形态）的检出召回。此前 v3 模型对这些新形态完全漏检（回归实测 30 帧仅检出 1 帧）。为验证"扩真实烟帧数"路线，已部署 v3 标注工作台并完成 v4 训练，本轮需决定 v4 成果以何种形态进入生产。

  • v4 训练：单类 smoke，从 v3 best 续训，84/100 epochs 早停（patience=20），最终 val mAP50=0.252（较训练中期 0.124 翻倍）；权重 best.pt 40.6MB。
  • 回归验证：DJI 4 张白天真烟帧，v3 全漏 → v4 全部检中（conf=0.10 口径）；生产口径 conf=0.25 下 v3 0/30 → v4 3/30（3 张 DJI 高置信检出）。
  • 已知短板：v2 老帧（远山零星小烟点）在 conf=0.25 下 v4 仍 0 检出——极小目标检测瓶颈仍在。
  • 部署发现：生产主引擎 straw-engine 为 3 类（smoke/fire/house）RT-DETR@960，而 v4 是单类 smoke，不能直接整体替换（会丢失 fire/house 检测）。
决策背景提示：v4 成果无法"即插即用"，必须选择一种部署形态，本报告对三条线路做诚实评估。

二、事实核查（评估前的前提更正）

评估过程中对两项关键前提做了服务器实测核查，结果直接改变了方案 B 的成本结构：

核查项实测结果影响
m6 3 类训练数据是否完整/video/shujuji/datasets/merged_v4/ 存在：train 6390 张，fire=12920 框 / smoke=3644 框 / house=446 框方案 B 无需从零标注 fire/house，成本大幅下降
v4 ONNX 部署链路已导出 best.onnx（80.9MB @1280），输出 [1,5,33600] YOLO 布局与 engine 解析兼容；GPU 推理 30.4ms（CPU 508ms 的 1/17）方案 A 技术可行性已验证
真实烟补帧速度回流 21 个对象无新增；司空作业当前不在线，截图采集器空转；当前仍 32 帧方案 C 的补帧周期不确定（可能以周/月计）

三、三条线路对比评估

方案 A独立 smoke 预检通道（v4 并行补检）

straw-engine 加载第二个模型 v4（低阈值），与 m6 的 fire/house 共存，并行补检小烟/远山烟。

评估维度分析
优点① v4 已验证 DJI 新形态 4/4 检出（m6/v3 全漏），司空作业在线时有补充价值 ② 不动 m6，fire/house 告警零风险 ③ 部署快（约半天），ONNX/GPU 链路已验证 ④ 可灰度对照
缺点① 未解决核心痛点：v2 老帧（远山小烟，召回低的根源）在 conf=0.25 下 v4 依然 0 检出——A 是"场景覆盖"，不是"能力提升" ② 司空作业恰不在线，部署后大概率长期无验证信号 ③ 低阈值（0.10~0.25）有天空大框误报前科（m7 实测），需确认器把关 ④ 双引擎告警去重/合并/统计口径，长期运维复杂度 ⑤ 数据未变，能力天花板未变

一句话评价：伪即时价值——只补"司空作业在线"这一场景，而该场景当前不存在。

方案 B3 类 v5 训练后整体替换（修正版）

将 merged_v4（3 类大样本）与 v5 新形态真烟帧合并，训练 3 类 v5，替换 m6 主引擎。

评估维度分析
优点① 成本骤降：merged_v4 已有 3 类 6390 张（fire 12920 / smoke 3644 / house 446），无需从零标 fire/house ② 单引擎最简架构，完全兼容现有引擎 ③ 数据红利最大：大样本保住 fire/house + 注入 DJI 新形态真烟，双赢 ④ 可量化对比：v5_3cls vs m6 同评估集比 mAP/召回，诚实验证提升
缺点① 比 A 慢：合数据 + 训练（1~2h）+ 验证 + 灰度，全程约 1~2 天 ② 合并有风险：类别 id 对齐、wechat/syn 与 merged_v4 是否重复需审计、标签质量参差 ③ house 仅 446 框仍是最弱类（与 m6 现状持平，不算回归） ④ 同样不解决"司空不在线"，但 B 目标本就是长期提升，不依赖即时验证

一句话评价：最接近"根治"的路线——数据红利 + 架构最优，且成本已被事实修正为可接受。

方案 C暂不部署，补帧到 100+ 再训 v5

v4 仅作评估基线归档，资源全投数据扩充，待真实烟帧凑齐 100+ 后直接训 v5。

评估维度分析
优点① 最诚实：承认数据不足是根因，资源全投数据 ② 零运维/架构风险 ③ v4 教训（真实烟帧有效、小目标仍难）直接喂 v5
缺点① 补帧速度完全不确定：回流 21 对象无新增、司空作业不在线 → 100+ 帧可能以周/月计，期间召回痛点无任何改善 ② 弃用 v4 已投入（一晚工作台 + 标注 + 训练） ③ "数据永远可以更多"无时间盒 = 完美主义陷阱 ④ 单类 v5 最终仍缺 fire/house，100+ 帧后还得回头合并 merged_v4——绕远路

一句话评价：最纯粹但最慢，且终点绕不开方案 B 的合并工作。

四、横向对比总表

维度 A 独立预检通道 B 3 类 v5 整体替换 C 补帧 100+ 再训
核心痛点解决否（远山小烟仍 0 检出）是（数据 + 架构双改善）远期是（周期不确定）
即时价值低（司空不在线，无验证场景）可量化对比验证无（纯等待）
数据依赖不依赖新数据merged_v4 现成可合并依赖司空作业产出（不确定）

架构复杂度双引擎去重/统计，长期负担单引擎最简无变化
风险误报需确认器把关合并审计风险（可控制）最小

共同瓶颈：三条线都受制于同一件事——司空作业在线 + 任务媒体产生，是突破"远山小烟漏检"的唯一数据资源。A 部署它、B 依赖它、C 等待它，但它当前不在线。

五、推荐结论：B 为主 + C 补帧后台并行

推荐：方案 B（3 类 v5 整体替换）为主，方案 C 的补帧作为持续后台任务

理由：① A 的致命伤是 v4 对生产痛点无效且无验证场景，不推荐为主；② C 的致命伤是没有时间盒 + 终点绕回 B 的合并，纯等是浪费；③ B 的第一步"数据集合并审计"（类别对齐/查重/样本量）不依赖司空作业，现在就能做——这是唯一可立即推进且有确定价值的动作。

落地步骤（按批次推进）

1
第 1 批 · 合并审计（约 0.5 天）合并 merged_v4 与 v5 数据集：类别 id 映射（m6 3 类 vs v5 单类）、图片级查重（wechat/syn 与 merged_v4 是否重叠）、标签质量抽查、样本量统计 → 产出合并后 data.yaml 与审计报告
2
第 2 批 · 训练与对比（约 2 小时）训练 3 类 v5（从 m6 best 续训，imgsz=960 与生产对齐）；同评估集上 v5_3cls vs m6 比 mAP50/召回，重点看 fire/house 不回归 + smoke 新形态提升
3
第 3 批 · 灰度与替换（约 0.5 天）导出 ONNX → FUHE 审查页挂 v5_3cls 灰度观察 → 达标后替换 config.json 顶层 model → 保留 m6 best.onnx 一键回退
4
持续 · 补帧后台任务直播截图采集 + MinIO 回流两个常驻进程继续跑，司空作业产生的任何新帧自动进入工作台，为后续 v6 迭代累积

六、冲突排查与风险回滚

风险点说明与对策
类别 id 对齐m6 3 类（smoke/fire/house）与 v5 单类（smoke）需建立映射；合并时统一 smoke 的 class id，避免标签错乱。审计报告逐类核验。
数据重叠wechat/syn 合成烟数据与 merged_v4 可能图片级重复，训练前按文件名/哈希查重，重复样本去重防止过拟合。
house 弱类仅 446 框，是三类中最弱类。预期与 m6 现状持平（不构成回归），后续可单独补标。
训练后不达标若 v5_3cls 在评估集上 smoke 召回不升或 fire/house 明显回落，则回到 C 路线继续补帧，不强行替换。
回滚方案替换仅改 config.json 顶层 model 指向 + 权重文件；m6 best.onnx 原样保留，一行配置即可回退，零数据风险。灰度期间双模型并行，可逐路对比告警。
