三、后端统一入库与"降噪"设计

3.1 单一入库入口

不论哪条通道，最终都调 store.insertWarning(w)（INSERT OR REPLACE，以 id 为主键），落 warnings 表：

列说明
id主键（iot-<recordId> / straw-<ts>-<rand>）
created_at⚠️ 格式不统一：iotcloud 存本地 YYYY-MM-DD HH:mm:ss，straw/cq_api 存 UTC ISO → 前端/聚合层需兼容两种（现由 parseWarningTime 兜底）
warning_typeiot-video-analysis / growth5h / cross / fixed
statuspending / handled（聚合组还有 partial）
data_json全量业务字段（source / aiType / picUrl / lat / lon / aiConfidence / bbox / streamId …）

3.2 聚合降噪（push_rules · 实测 5 条规则全启用）

规则名适用通道AI 类型时间窗阈值
堆头未覆盖ALL堆头未覆盖24h≥20 条
道路扬尘ALL道路扬尘24h≥1 条
秸秆燃烧ALL秸秆燃烧24h≥2 条
堆场扬尘ALL堆场扬尘24h≥20 条
AI视频24h≥5聚合ALL（通配）24h≥5 条

折叠逻辑（queryWarningsAggregated）：按 (通道, AI类型) 分组 → 窗口内命中数 ≥ 阈值 → 折叠成 1 条"聚合告警"（带 memberIds / count / maxLevel / confidence 范围）；未达阈值则原样平铺。
规则优先级：业务方「具体类型」规则 > 系统默认「通配」规则（否则通配抢先命中，自定义阈值失效）。

3.3 过滤规则（alert_filter_rules）· 实测 0 条

设计上用于"命中即从告警列表隐藏"（alertFilterRuleHit），支持按来源多选 + 等级 + 时间。当前一条都没配 —— 意味着所有告警都会进入列表，没有任何前置屏蔽，只能靠聚合降噪。

六、关键结论与风险点

6.1 三句话结论

  1. 累计占比≠日常占比：iotcloud 累计占 96.5%（28,988 / 30,035），但正常日均三通道量级接近（近 4 天：iotcloud 22~111、cq_api 5~28、straw 0~25 条）。该占比被 09-06~09-10 的 5 天异常爆发（合计约 20,567 条）严重拉高。
  2. 频率三档：视频=事件驱动；气体=固定 5 分钟整点；秸秆=事件驱动（有烟才有）。正常日均总计约 50~120 条，但一旦某通道抖动，单日可冲到 5,000 条量级。
  3. 接收以轮询为主：4 种机制里只有 SSE（无人机）是真推送，告警本身全靠 10s 轮询 → 告警可见延迟最坏 10s。

6.2 值得注意的风险 / 缺口

#问题影响
1created_at 两种时间格式混存（本地串 / UTC ISO）排序、24h 窗口、跨天分区都要靠兜底解析；历史踩过"通道 null"、"聚合误判过期"等坑
2告警无 WebSocket 推送（仅 SSE 给无人机）大屏值班最坏 10s 后才看到；提示音只在历史弹窗打开时才 diff
3首次进页仅回灌 10 条（DashboardContext slice(0,10)）告警多时早期聚合告警不显示（P2 已修 AlertPanel 侧不被挤出，但源头仍是 10 条窗口）
4过滤规则 0 条无前置降噪，仅靠聚合折叠；一旦某通道噪声升高会直接刷屏
5MQTT 未连接（UI 显示"未连接"）MQTT 通道配置存在但未实际使用，采集预警的浏览器直推能力闲置
6城运通道 0 条数据代码/规则/推送链路都就绪，缺真实对端数据 → 该通道等于未验证
709-06~09-10 异常爆发未复盘（连续 5 天 3,373~5,220 条/天，合计约 20,567 条，占累计 68%）若复发会直接刷屏并压垮前端（10s 轮询 + 列表渲染），且掩盖真实告警

6.3 若要"更实时"的改造方向（供参考，未开工）

  • 告警统一改 SSE/WS 推送：后端入库后广播，前端订阅 → 延迟 10s → <1s（复用现有 SSE 基建，改动量中等）
  • 提示音移到全局：不必打开历史弹窗才 diff，直接在 externalAlerts 层 diff 新告警
  • 统一时间格式：入库时全部转 UTC ISO（或全部本地），消除兜底解析
  • 补几条 alert_filter_rules：把已知稳定误报（如夜间某通道）前置屏蔽，减少刷屏
