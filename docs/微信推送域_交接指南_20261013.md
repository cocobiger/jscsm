## 3. 这条链路是怎么跑的（两条推送链路别混）

| | **链路 A · 秸秆**（本域主角） | 链路 B · IoT 视频分析 |
|---|---|---|
| 触发 | `straw-engine` 自研模型 | `IoTCloud`（172.16.8.11）外部平台 |
| 入口 | `POST /api/straw-alert` → `strawWorkflow()` | `iot-fetcher.js` → `warnings` |
| 末端 | **责任映射 → 微信桥**（`area_responsibility.webhook`） | 智治推送 / 城运（`cyzx.js`） |
| 痕迹字段 | `warnings.data_json.wechatPush` | 无 |

**链路 A 的推送流程**：告警 → `reverseGeocode` 坐标反查乡镇 → `store.findResponsibility(town, community)`
→ 取该行 `webhook` → `sendWechatPush(webhook, …)`（带重试 + 桥误报识别）→ 桥 `POST /send?group=<会话名>`
→ 桥用 `wechatauto` 驱动本机微信发送。

> ⚠️ **判据铁律**：`warnings.data_json` 里没有 `wechatPush` **不代表推送失败** —— 那多半是链路 B 的告警。

## 4. 「微信登录」功能点（本次新建，已上线）

### 页面位置
`src/app/components/admin/StrawMonitorPage.tsx` → tab `responsibility`「责任映射 / 微信群推送」
→ `ResponsibilityManager` 顶部挂 `<WeChatLoginPanel />`。

### 后端 `server/wechat-login.js`（7 个路由，**全部 adminOnly**）
| 端点 | 作用 |
|---|---|
| `GET /api/wechat/status` | 在线状态 + 二维码码龄 + `resetting` + `updating`；桥状态 3s 缓存 + 并发去重 |
| `GET /api/wechat/qr` | 二维码 PNG（`no-store`；已登录返回 409） |
| `POST /api/wechat/qr/refresh` | 落 `wxb_qr/reset.request` → 202；120s 内重复点返回 `alreadyPending` |
| `GET /api/wechat/targets` | 群/个人清单（服务端拼好 `webhook`）；`?q=` 过滤；30s 缓存 |
| `POST /api/wechat/test-send` | 向指定会话发测试消息（复用 `sendWechatPush`） |
| `GET /api/wechat/default-target` | 全局默认对象 + `backup{at,by,rows}` |
| `PUT /api/wechat/default-target` | 设默认对象；`applyToAll`（默认开）**同步改写全部责任行的 webhook** |
| `POST /api/wechat/default-target/rollback` | 按快照还原上一次同步 |

**批量同步的安全设计**（改这里之前先读）：**先快照再改** —— 受影响行的
`(id, town, community, 原 webhook)` + 逐行回滚 SQL 存进 `kv_config.wechat_default_apply_backup`；
然后用应用自己的幂等 upsert（`store.importAreaResponsibilities`）**只替换 webhook**，
保留 `unit/person/phone/remark`。前端有二次确认，且改动后可「恢复上一批改动」。

`server/…` 无关，在 `infra/wechat-bridge/wechat_bot_server.py`。

## 5. 🔴 铁律与判据（这一节最容易踩，务必读完再改）

### 5.1 「微信是否已登录」的正确判据
**❌ 不能用** `/health` 的 `driver/sessions/wechat_version` —— 那是 `_refresh_cache()` 填的，
全文件仅 1 处调用（发送成功路径），没推送过时永远是 null。

**❌ 更不能用**「能读 DB + 有会话/群数据」—— **被顶下线后磁盘 DB 仍可解密**
（`DRIVER`/`DRIVER_NAME` 是模块级永久缓存；`WeChatDB` 密钥缓存在 `workdir/keys.json`），
session/chat_room 依旧有数据 ⇒ **这个证据会永远为真**（2026-10-13 实际故障）。

**❌ 不能按窗口标题挑**：被顶下线时的「提示」弹窗标题居然是 `Weixin`（复用主窗口标题）。
**❌ 不能按「登录窗是否存在」判**：登录窗在已登录时也可能残留。

**✅ 正确判据 = 窗口尺寸 + 「有没有主窗」**：
| 观测 | 判定 |
|---|---|
| 有**主窗**（宽 ≥700 且 高 ≥500，实测 **896×648**） | 已登录 |
| 只见**小窗**（宽 ≤420 且 高 ≤460） | **未登录（硬否决，不看 DB 证据）** + `reset_driver()` |
| 完全看不到微信窗口 | 才退回 DB 证据（可能最小化到托盘） |

实测到的三种"小窗"：登录窗 `296×388`（标题`微信`）｜被顶下线提示弹窗 `330×314`（标题`Weixin`）｜
自动更新窗 `548×380`（标题`weixin update`，落在尺寸死区，需单独识别 `updating`）。

### 5.2 二维码判据不能只看体积
微信 **4.1.13.65 起登录窗默认显示「账号卡片」**（头像+昵称+「登录」+「切换账号」），
**必须点「切换账号」才出二维码**。头像让该区域 PNG 达 3297B，**骗过了原「≥2500B」下限**。
| 区域 | PNG 体积 | 暗像素占比(<110) |
|---|---|---|
| 真二维码 | 4155–8935 B | **0.473 ~ 0.489** |
| 账号卡片（头像） | 3297 B | **0.036** |
⇒ 判据 = 体积 ≥2500B **且** 暗占比落在 **0.30~0.62**（226 已装 `python3-pil`）。

### 5.3 桥的重复监听事故面
**Windows 默认允许两个进程 bind 同一端口**（Werkzeug 开 SO_REUSEADDR）。
曾同时存在 Session 0（WMI 直启遗留，**看不到微信窗口 ⇒ 发送必败**）与 Session 2（正确）两个实例。
⇒ **重启桥必须把所有监听 18888 的 PID 全杀**，确认端口释放后再
`schtasks /Run /TN WeChatBridge`（`/IT` ⇒ 交互式会话）。收官检查：**只能 1 个实例且在 Session 2**。

### 5.4 高危动作规范（项目通用）
批量改写 / 下发类操作必须走 **dry-run → 确认 → 批量应用 + 快照可回滚**。本次批量同步 52 行即按此实现。

## 8. 坑清单（换机后仍会遇到）

### 8.1 访问与凭据
- **`ssh` 端口 22233**（22 不开是正常的）；**`scp` 端口要大写 `-P 22233`**（小写会报 "Not a directory"）。
- 本机 Git Bash 下 **`sshpass` 不可用**（拿不到 pty ⇒ 一直 `Permission denied`，**极像密码错**）
  ⇒ 用 **`SSH_ASKPASS`**：`export SSH_ASKPASS=<脚本> SSH_ASKPASS_REQUIRE=force DISPLAY=:0`，
  再 `-o PubkeyAuthentication=no -o PreferredAuthentications=password`。
- 桥机凭据在 **`/root/.wxbridge.env`**（600，**不入仓库**）。VM 操作通道 = **WMI over SMB（`/usr/local/bin/wmiexec.py`）**。
- **`EnvironmentFile=/data/HBJSC/backend/iotcloud.env`**（含 `GAS_ALERT_SECRET` 等）。

### 8.2 沙箱/工具链（多数是"静默失败"）
- **Write 落盘是 CRLF** ⇒ `ssh "bash -s" <脚本` 里内层 heredoc 结束标记会变 `PY\r` ⇒ bash 吞掉后半段。
  **一律 `tr -d '\r'` 剥 CR + `scp` 成文件后 `bash /path.sh`**。
- **不要把嵌套引号+中文塞进 `ssh "…python3 -c \"…\"…"`** —— 本地 bash 会解析崩（`unexpected EOF`）。
  **写成脚本文件 + `bash -s` 喂进去**。
- **长脚本要分段跑**：本地 `timeout 600 ssh …` 会在内部 sleep 太多时 SIGTERM，表现为"无输出"。
- **后台 `&` 起的 SSH 隧道会随该条命令的 shell 退出被回收** ⇒ 表现为"第一次成功、后面全 502"。
  正确姿势：**`ssh -N -f -L 18080:127.0.0.1:80 …` 与探针写在同一命令里**。
- **本机环境有 `HTTP_PROXY/HTTPS_PROXY`（沙箱网关）** ⇒ headless 浏览器页面内 `fetch` 会失败
  （`TypeError: Failed to fetch`），而同时 `curl` 直连隧道是 200，**极易误判成服务端故障**。
  `scripts/ui-probe.mjs` 已加 `--no-proxy-server` 并清理子进程的代理环境变量。
- **`wmiexec` 输出首行是空行** ⇒ `head -1 | awk '{print $NF}'` 会得到空值（解析 PID 时踩过）⇒ 用 `grep -oE '[0-9]+$'`。

### 8.3 前端
- **本仓 `src/` 现在就是生产前端真源**；发布 = `npm run verify` → 传 `index.html` + `assets/`
  （**纯静态替换，不重启后端**，可整目录回滚）。
- **发布前仍要跑功能对照门禁**：拿线上 bundle 与本机构建做中文文案差集，
  若出现"线上有、本机没有"的**页面级文案** ⇒ **停手**，先确认基线是否落后
  （2026-10-13 靠这道门禁拦下过一次大范围回退）。
- 真源自带的 `*.bak_*` / `*.retired_*` 也在库里 —— 它们是那些**已下线页面的唯一副本**，别删。
