③ 方案对比与推荐（每方向给 A/B/C）

方向一：批量导出增强

A · 前端补齐筛选 + 后端流式导出 推荐
新增 GET /api/warnings/export（status/source/level/from/to/q），服务端按条件全量查（上限 50k）直接写 CSV 响应；前端筛选栏加时间范围＋来源，导出走新接口。彻底解决 E1/E2/E3，E4 聚合明细用"勾选展开明细"缓解。改动可控（1 接口 + 1 页面）。
B · 仅前端修（不动后端）
把 limit 提到 5000、列补来源、导出当前筛选。1~2 小时能交付，但 E1 换汤不换药（5k 也截断）、E2 无解——导出仍是"近 N 条"而非"某时间段"。
C · 分页式列表大重构 + 导出
列表改服务端分页（cursor/页码）再叠加导出。工程量大、与 10s 轮询/聚合折叠/乐观更新纠缠，收益主要落在浏览而非导出。第四批不建议，留作远期列表优化独立课题。

推荐 A：导出是"数据带走"场景，服务端全量是唯一正确解；前端筛选补齐时间范围能让"导出 = 我看到的筛选结果"，语义闭环。

方向二：研判依据详情联动

A · 事件总线轻刷新 + 弹窗互通 + 归因持久化 推荐
把 alerts:reload 整页刷新改为 alerts:refresh 局部刷新事件（AlertPanel 与 AlertHistoryModal 各自订阅并 reload 自身）；告警记录弹窗聚合行加「研判依据」入口复用 AlertEvidenceModal；handle-group 支持可选 verdict/note 写回 data_json（J3 持久化）。同时解决 J1/J2/J3，J4 顺带做单行证据查看。
B · 只加入口，不动刷新与归因
仅把「研判依据」按钮接进告警记录弹窗。半天交付、风险最低，但处置完仍是整页 reload（弹窗被关）、误报归因仍旧丢失——体验只补一半。
C · 双弹窗合并大重构
把 AlertHistoryModal 与 AlertEvidenceModal 合成一个"告警工作台"（列表+详情分栏）。体验最完整，但要动 DashboardContext 告警数据流与两个既有组件的 props 契约，回归面大，超出"体验打磨"范畴。

推荐 A：J2 的整页刷新本质是"用 reload 偷懒做状态同步"，现在有了 10s 轮询与乐观更新，完全可以用局部刷新替代——这是本次打磨里技术债收益最高的一笔。

方向三：微信卡片优化

A · 秸秆链打磨：状态可视化 + 复查直达 + 失败重试 推荐
W2 推送状态页（后台加 Tab 展示 wechatPush 成功/held/失败/更正）；W3 markdown 内容加"驾驶舱/复检页直达"入口；W4 失败自动重试 1 次 + 模板可配项扩展。纯后端+一个管理页，不碰既有推送主流程语义。
B · 在 A 基础上 + 四来源通用推送订阅
新增 alert_push_channel 表＋"推送订阅"管理页＋ingest 触发 hook，让气体/AI 视频/城运告警也能按规则推企微群。价值大但是新功能级：涉及 4 来源数据结构差异（AI 视频无行政坐标、城运有自身回调）、群映射、频率抑制（防 AI 高频刷屏）、与 alert_filter_rules 的交互语义，需单独评估排期。
C · 暂缓微信方向
本批只做导出与研判联动，微信推送打磨放到秸秆复检链路（straw-engine）下一轮一起做。若当前微信群推送稳定、无人反馈，可接受。

推荐 A，B 需另拍板：W2（推送状态可视化）优先级最高——任何推送系统"静默失败"都是运维事故源。W3/W4 属低成本高感知。B 的通用订阅建议单独出一份评估（涉及业务规则确认：谁可以收到什么告警），不夹带在本批。

⑤ 冲突排查与依赖（按已实施代码逐条核对）

#冲突点分析结论 / 处理方式
C1导出 vs alert_filter_rules 5 维过滤过滤规则语义是"驾驶舱展示降噪"，导出是"数据带走"——导出不应悄悄应用个人过滤规则（否则报表缺行），导出条件由用户在导出面板显式选。结论：T14 服务端过滤与 alertFilterRuleHit 完全解耦，文档注明差异。
C2source 归一化 vs 现有"前端推断"兼容逻辑resolveSource() 仍保留作兜底（防漏网），T13 修补后以 data_json.source 为准——两处规则必须同一份（建议后端常量导出，避免二次漂移）。
C3alerts:refresh 改造 vs 10s 轮询竞态守卫AlertHistoryModal 已有 seqRef 丢弃过期响应，refresh 触发 load() 会自然被守卫保护；AlertPanel 侧需确认自身没有同类竞态（走查其 externalAlerts/selectedAlertId 状态）。
C4弹窗内复用 AlertEvidenceModal 的 zIndex / 双层滚动AlertEvidenceModal zIndex=2000 天然盖住告警记录弹窗(1000)；其容器 flex 居中不阻塞父弹窗；处置完成后由 refresh 事件驱动父列表更新，无需关闭父弹窗。需验证 confirm/toast(z1100/1200) 不遮挡子弹窗按钮。
C5handle-group 扩展 verdict 字段 vs 既有调用方现行调用点 3 处：AlertHistoryModal.handleGroup（聚合标记）、AlertEvidenceModal.handleGroup(valid/false)、路由 handle-all。verdict 为可选字段，向后兼容；handle-all 不带 verdict 不落 review，语义保持"批量清空"。
C6wechatPush 回写硬编码 DB 路径strawWorkflow 直接用 new DatabaseSync('/opt/jsc/backend/data/jsc.db')——本地开发无此路径会抛错（已有 try/catch 仅日志不阻断，容错 OK），T19~T21 改动时顺带改为复用 store 实例，消除硬编码。
C7导出时间范围的时区语义created_at 存 UTC ISO 串，T14 的 from/to 需按 Asia/Shanghai 转换（沿用 warningTrend 的 +8h 处理），否则 8 月报表会差 8 小时边界。
C8T10 轮询与"已处理 tab"数据量双请求每 10s 各拉 500 条，若 T22 引入服务端分页需同步改轮询策略（保持"pending 只拉未处理+聚合"，handled 按需翻页），避免每 10s 全量 1000 行解析。
