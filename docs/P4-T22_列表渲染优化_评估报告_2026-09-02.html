一、背景与目标

背景：「告警信息管理」弹窗（AlertHistoryModal）未处理 + 已处理 tab 在生产环境已积累 506 条告警，其中已处理 491 条。用户反馈弹窗内滚动卡顿（特别是已处理 tab 滚到中段时帧率明显下降）。

目标：通过分页 / 虚拟化 / DOM 精简等手段，确保 500+ 条数据下弹窗滚动流畅（目标 ≥ 50 FPS），同时不破坏已实施的 T15（导出增强）/ T23（新告警 toast）/ T24（会话态保持）功能。

实施顺序：P4 三批 T23 → T24 → T22，前两项已交付 commit c43c195。本报告为 T22 实施前的方案评估。

说明 headless 无 GPU 加速会拉低 FPS，但 144ms/帧 vs 16.7ms/帧 8.6× 差距远超 GPU 因素（约 1.5-2× 影响）——真实浏览器同样会卡顿，仅绝对值略高（如真实环境 30-40 FPS，但用户体验已差）。

卡顿根因（推断）

  1. 491 行全部驻留 DOM，scrollTop 改变时浏览器需对所有 overflow:hidden 容器内的 6000+ 节点重做 layout/paint（paint 永远跑，layout 在含 transform/position:absolute 时不跑）
  2. 每行 position:relative + 多层嵌套 + 条件徽标/置信度文字节点，scrollTop 变化触发滚动关联 reflow
  3. headless rAF 锁在 60fps 但 144ms/帧说明 1 帧内 React 没渲染完所有 dirty 节点 + paint 未结束
  4. React.memo 对此场景帮助有限（DOM 节点全在，rerender 优化不解决 paint 开销）

关键判断

  • 行高不定：聚合行展开后从 ~60px 撑到 ~250px（5 成员），虚拟化需动态测量——react-virtuoso 表现 OK，但代码量翻倍
  • 业务量级：当前 506 条，预估 1 年内 < 2000 条；分页足够覆盖
  • 风险偏好：用户偏好「长期彻底方案」（记忆），但也强调「分页切片/虚拟滚动」是用户拍板时给的并列选项，无强偏好
  • 实施代价：A 可 1 小时实施 + 1 小时验收；B 需 2-3 小时实施 + 2 小时验收

四、推荐方案 A 落地步骤

推荐方案 A（分页切片+无限滚动）：基于实测数据（500-2000 条）+ 行高不定 + 与 T23/T24 兼容性 + 0 依赖，分页是当前业务量级的最佳性价比选择。同时 C（memo+DOM 精简）作为附带优化（仅当 A 实施后仍不达标时启用）。
1前端数据层分页
  • 新增 displayLimit state（默认 50）
  • displayList = tab==='pending' ? pending.slice(0, displayLimit) : handledList.slice(0, displayLimit)
  • 列表底部 IntersectionObserver sentinel 触发 setDisplayLimit(n => n + 50)
  • tab 切换时 setDisplayLimit(50) 重置
2兼容 T23 轮询 diff
  • diff 在 flat + aggregates 全量上做，不变
  • 新告警的 toast / 角标立即显示在列表顶部（已加载），无感知差异
3兼容 T24 展开态
  • 展开 id 在 expanded Set 持久化（sessionStorage 已有）
  • 当展开 id 对应行尚未加载（>displayLimit），UI 不显示但 state 保留，滚到该位置后自动展开
  • 增强项：toast 提示「新告警已到达第 N 条」+ 「跳到」按钮（可选 v2）
4UI 反馈
  • 列表底部「加载中…」sentinel（IO 触发时）
  • 已加载完毕时显示「已显示 X / Y 条 · 顶部 ↑」（含回到顶部小按钮）
  • keyword 筛选时 displayLimit 重置为 50
5验收（headless shot_t22.cjs）
  • FPS 复测：> 50 FPS（500 条下）
  • 滚到底 → 新增 50 条 DOM 行可见
  • 切 tab → displayLimit 重置 50
  • 搜索 't22test' → displayLimit 重置 50 + 全量过滤生效
  • 导出 CSV → 服务端接口不变，不影响
  • T24 展开 id 跨 session 恢复 + 展开行在已加载切片中
  • T23 轮询 diff 不变，toast 仍弹
6性能优化（仅当 A 不达标时）
  • 每行 React.memo + 稳定 key
  • 合并 1-2 层嵌套 div 减少节点
  • Tab 切换时 React.lazy + Suspense 延后列表挂载

六、风险与回滚

风险影响缓解回滚
分页导致用户漏看底部数据 中 底部「加载更多」sentinel + 「已显示 X/Y」+ 顶部按钮 移除 sentinel，displayLimit 改 9999
T24 展开 id 在未加载切片不可见 低 state 保留，滚到时自动展开 可忽略
keyword 搜索后 displayLimit 重置导致用户已滚到底的视图丢失 低 keyword 变化时 setDisplayLimit(50)（合理） 不重置（保持 displayLimit）
与 T15 导出筛选面板（expSources/expLevels）混淆 无 导出筛选独立 sessionStorage key jsc:alert-export-sess（如未来需要） 无影响
性能仍不达标（< 50 FPS） 低 叠加方案 C：React.memo + DOM 精简 git revert commit 回到 T24

回滚方案 T22 实施为独立 commit（预计 hash 类似 abc1234），生产部署前在 sky 备份目录 /opt/jsc/frontend/backups/t22_bak/ 留存 T24 版本。任意异常 1 条命令回滚：cd /opt/jsc/frontend && cp -a backups/t22_bak/* . && rm -f assets/index-zoRLADhB.js。

七、结论与下一步

推荐方案 A：分页切片+无限滚动

依据：

  • 实测数据：500 条 7.2 FPS → A 方案预期 50-60 FPS（8× 提升）
  • 行高不定（聚合展开 + 图片）天然兼容
  • 0 依赖、80 行代码、1 小时实施
  • 与 T23/T24 兼容性已逐一排查，无破坏性风险

下一步：等待用户拍板后实施 + 验收，预计 1.5-2 小时交付 commit。

可选追加

  • 方案 A 实施后若 FPS 仍不达标（< 50），追加 C（React.memo + DOM 精简），预计 30 分钟
  • 若 1 年内告警量级超 2000 条，可升级到方案 B（react-virtuoso），需 2-3 小时改造
  • 方案 A 验收脚本 tmp/shot_t22.cjs：FPS 复测 + 滚到底断言 + 搜索/导出兼容性
