二、阶段划分（以"明天真飞"为第一约束）

阶段 A：明天真飞前（可选增强，不阻塞真飞）
序任务工作量说明
A1拉流进度反馈（弹窗"接入中"加进度条/预估）0.3 天成本最低，让明天真飞体验更好

说明：当前已修好的「hls 相对路径 + 原流优先 + 失败回退 + OSD 兜底」已构成最小可用集，明天真飞已能出画面。阶段 A 的任务是可选增强，做不做不影响真飞成功率。

阶段 B：明天真飞后（按价值 + 依赖排序，推荐执行顺序）

T1 端到端 smoke test（最高优先级）

项内容
目标每次部署后自动跑"模拟起飞→弹窗→拉流→播放"全流程，阻断潜伏 bug
子任务① 复用 DroneSimPanel 模拟起飞事件 ② 自动推测试流到 ZLM ③ 校验 stream-status 返回 + hls 可达 ④ 校验弹窗状态机状态 ⑤ 输出 pass/fail 报告
依赖DroneSimPanel（已有）+ 测试流推送脚本（已用 ffmpeg 验证过）
工作量1 天
验证指标下次真飞首次成功率（目标：一次通过，不再现"修完再真飞"循环）

T2 触发状态可视化 + T3 拉流进度反馈（合并批次）

项内容
目标解决"不可预期"核心痛点：无人机起飞后，弹窗出现前有全局状态反馈；弹窗接入中有进度提示
子任务① T2 地图机场卡片/顶部状态栏加"无人机状态指示灯"（在仓/起飞中/流接入中/直播中，数据源 OSD droneInDock + SSE）② T3 弹窗"接入中"加进度条（基于 mirror 平均 9~15s 预估）
依赖OSD 数据（已有）+ 前端展示改动
工作量0.8 天（两项合并，都是前端展示层）
验证指标"以为系统坏了"的误判率 ↓；等待放弃率 ↓

T4 诊断面板

项内容
目标排查从 30min 级降到分钟级：后台加"弹窗链路自检"四段状态灯
子任务① 后台新面板：SSE 连接状态 / 最近事件源（webhook/OSD兜底）/ 拉流状态（sikong_ 在线）/ 播放状态 ② 每段绿/黄/红状态灯 + 最近 10 条事件流水
依赖链路各段状态数据（已在 drone-events / zlm-watcher 有）
工作量0.5 天
验证指标MTTR（平均修复时间）↓

T5 实时标框重构（业务核心，成本高）

项内容
目标真正实现"实时标框"：放弃低帧率带框流，改为"原流 + SSE 推 bbox + 前端 canvas 叠加"
子任务① 后端 straw-engine 检测结果经 SSE 推 bbox（x/y/w/h + 类别 + 置信度）② 前端弹窗 canvas 叠加绘制检测框 ③ 带框流降级为"检测快照"（告警时保留，不做主画面）
依赖straw-engine 检测输出 + SSE 通道 + 前端 canvas
工作量2~3 天
验证指标检测框实时可见（30fps 原流上叠加，不卡顿）
说明业务核心诉求，但成本高、需单独设计；建议真飞链路稳定后再启动

三、任务依赖关系

T1（smoke test） 独立，最高优先级 T2/T3（可视化+进度） 独立，可合并批次 T4（诊断面板） 依赖链路数据（已有），独立可插 T5（标框重构） 独立，但成本高，最后启动

四、推荐执行顺序 + 拍板点

批任务工作量说明
批1T1 端到端 smoke test1 天防下次真飞暴露潜伏 bug，最高优先级
批2T2 触发可视化 + T3 进度反馈0.8 天解决"不可预期"核心痛点
批3T4 诊断面板0.5 天提升排查效率
批4T5 实时标框重构2~3 天业务核心，最后启动

五、结论

① 明天真飞已能出画面（最小可用集已完成），阶段 A 的进度反馈是可选增强；
② 真飞后推荐顺序：T1 smoke test（防潜伏 bug，最高优先级）→ T2/T3 可视化+进度（核心痛点）→ T4 诊断面板 → T5 标框重构（业务核心，最后）；
③ 合计工作量：T1~T4 约 2.3 天，T5 另计 2~3 天；
④ 建议拍板：确认执行顺序（推荐批1→批2→批3→批4），或调整批次后开工。
