IoTCloud 视频分析记录中断 · 调查与解决方案

对象：物联网视频分析平台 172.16.8.11（对外 111.10.220.226:6881） · 通道 56331706881318000004（九龙沙场）
调查时间：2026-07-09 · 方法：仅只读探测 IoTCloud 接口，未修改任何物联网服务器代码
根因定性：IoTCloud AI 分析服务全局中断（2026-06-08 14:50:02）

一、现象描述

用户在 IoTCloud 后台查看通道 九龙沙场（channelSipId=56331706881318000004， deviceSipId=50010100001310000001）的分析记录，发现：

  • 最新一条记录时间为 2026-06-08 14:50:02；
  • 此后至今（2026-07-09，约 31 天）持续无任何新分析记录；
  • 该通道记录总数固定为 30 条，时间跨度仅 2026-06-05 → 2026-06-08。
用户提供的访问地址 /video/analysisRecord?... 经实测返回 404——该路径并非真实数据 API。 真实接口为 /prod-api/sip/analyse/record/list。地址本身不是记录缺失的原因。

2.2 单条记录样本（说明记录性质）

{ "recordId": 83387, "deviceSipId": "50010100001310000001", "channelSipId": "56331706881318000004", "createTime": "2026-06-08 14:50:02", "analyseInfo": "[{\"unsoilcover\":0.54}]", "ruleId": 163, "picUrl": "http://111.10.220.226:5001/images/detect/2026/06/08/2026-06-08T14:30:20.jpg", "deviceName": "NVR", "channelName": "九龙沙场", "confirm": 0 }

记录为周期性 AI 快照（约每小时一条，带 ruleId=163 与固定算法 unsoilcover）， 并非“有事件才产生”。这类定时任务一旦中央调度停止，所有通道会同时停更——与 2.1 的现象吻合。

2.3 排除项（确认非 JSC 侧 / 非过滤导致）

JSC 拉取逻辑无日期过滤 ✅

JSC 后端 iot-fetcher.js 每轮仅请求 pageNum=1&pageSize=20 并按 recordId 去重，没有任何 beginTime/endTime 限制。 只要 IoTCloud 有新记录，首屏（最新 20 条）必然包含，会自动流入 JSC。因此“看不到新记录”是源端没有，不是被我们漏拉。

IoTCloud 的 beginTime 参数无效 ⚠️

实测以 beginTime=2026-06-09/06-20/07-01 查询，均返回 total=30 且是同一批旧数据。 说明该列表接口的日期过滤参数未生效（字段 beginTime/endTime 恒为 null）。这本身是一个接口缺陷，但不影响结论： 按 createTime 降序的首页最新记录就是 2026-06-08 14:50:02，全量仅 30 条。

三、根因分析

中断发生在 2026-06-08 14:50:02，且 9 路通道同步、记录为定时快照——指向中央 AI 分析服务在这一刻停止写库。 结合“距今约 31 天（≈1 个月）”的时间特征，按可能性排序如下：

可能性 ★★★★★（最高）

AI 分析 License / 授权到期

厂商按“路数×时长”授权，授权在 2026-06-08 前后到期，分析模块停止出图与写库。与“整月空窗”高度吻合。
可能性 ★★★★☆

AI 分析服务 / 定时任务被停止或崩溃

中心调度进程（如 analyse-scheduler）在 14:50 宕掉或被人停用，所有通道快照随之中断。
可能性 ★★★☆☆

分析规则 ruleId=163 被禁用 / 删除

该全局规则被关闭后，绑定它的全部通道不再产生记录。属中央配置变更。
可能性 ★★★☆☆

存储 / 写盘异常

检测图落盘目录 images/detect（111.10.220.226:5001）或数据库写满/只读，导致分析任务无法落库。
可能性 ★★☆☆☆

NVR / 视频源整体断流

若 9 路同属一台 NVR，NVR 掉线也会导致无视频可分析。但“全部通道同秒停”更偏中央而非单 NVR。
可能性 ★☆☆☆☆（已排除）

JSC 侧拉取 bug / 前端显示问题

已排除：JSC 无日期过滤；IoTCloud 源端本身无新数据；前端 apiFetch bug 此前已修复且当前接口返回 9 通道正常。

四、解决方案

因无法改动物联网服务器代码，解决分两层：A. IoTCloud 运维侧恢复（治本，必须做）；B. JSC 侧增强（治标/防复发，可选做）。

A. IoTCloud 侧排查与恢复（运维动作，非代码）

  1. 确认 AI 分析模块状态：登录 IoTCloud 管理后台 → 算法/AI 分析 → 查看分析服务与“定时分析任务”是否处于运行中。若已停止，重新启用并观察是否恢复 hourly 快照。
  2. 核查 License / 授权有效期：重点看授权到期日是否落在 2026-06-08 前后。若是，联系厂商续费/重置授权即可恢复（最高概率根因）。
  3. 检查分析规则 ruleId=163：确认该全局规则未被禁用/删除，且其调度计划覆盖到当前日期。
  4. 检查存储与写盘：查看 images/detect 目录与数据库磁盘使用率，确认未写满/只读；必要时清理或扩容。
  5. 检查 NVR 与视频源：确认 9 路通道所属 NVR 在线、视频流正常（可在 IoTCloud 实时预览验证）。
  6. 查看服务日志：检索 IoTCloud 在 2026-06-08 14:50 前后的应用/调度日志，定位停止瞬间的报错（授权失效 / 任务异常 / OOM 等）。
  7. 重启分析服务：完成上述确认后，重启 AI 分析相关服务进程；约 1 小时内应开始出现新记录。

B. JSC 侧增强（防止“无人察觉”式中断，可选实现）

JSC 目前只是被动拉取，IoTCloud 一旦断供，驾驶舱会静默无新告警，难以第一时间发现。建议在 JSC 增加数据新鲜度监控：

监控逻辑
每轮拉取后，记录各通道最新 createTime；若距当前 > 阈值（建议 24h，AI 快照为 hourly）则在后台/大屏标记“分析数据中断”。
前端呈现
在“AI分析存档”列表与地图摄像头信息窗显示“最近分析：YYYY-MM-DD HH:mm”，陈旧即变灰/告警色。
恢复自动衔接
JSC 拉取逻辑无需改动：IoTCloud 恢复后，新记录出现在首页，按 recordId 去重自动入库。

以下为可选的后端监控代码片段（示例，未部署）：

// iot-fetcher.js 伪代码：每次 fetchOnce 后更新新鲜度 const FRESHNESS_MS = 24 * 3600 * 1000 for (const ch of channels) { const latest = _store.latestWarningTime(ch.channelSipId) // 取该通道最新 createTime const stale = !latest || (Date.now() - new Date(latest).getTime()) > FRESHNESS_MS _channelStale[ch.channelSipId] = stale } // 暴露给后台：GET /api/iot-analysis/freshness -> [{channel, latest, stale}]

五、恢复后验证步骤

  1. 在 IoTCloud 后台确认该通道出现 2026-06-08 之后的新分析记录（或直接调 /sip/analyse/record/list 看最新时间是否后移）。
  2. 等待 JSC 下一轮拉取（≤30s），在 JSC 后台“AI分析存档 / 通道接入”确认新记录流入、地图摄像头出现对应告警。
  3. 观察 JSC 日志 journalctl -u jsc-backend -f | grep "[IoT]" 出现“拉取完成 … 新增N条”。

六、结论

分析记录缺失的根因在 IoTCloud 侧——其 AI 分析服务在 2026-06-08 14:50:02 全局停摆（9 路通道同秒中断、记录为定时快照）， JSC 拉取链路无过滤、无故障，属被动受影响。最高概率原因为 AI 分析 License 到期或分析服务/定时任务被停止。 恢复需 IoTCloud 运维侧续期/重启服务（A 项），并建议补充 JSC 侧新鲜度监控（B 项）以便今后及时发现。
