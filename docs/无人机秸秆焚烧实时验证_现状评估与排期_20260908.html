一、结论摘要

现有系统已满足约 70%，核心链路（检测→标框→坐标定位→乡镇→入库→人工确认）已全部打通，但「弹窗画面实时标框叠加」这一环是缺口，且坐标定位依赖的无人机 OSD 字段需真飞确认。

一句话：检测和事件生成的后端链路基本就绪；差的只是"弹窗画面里实时画框"这个前端可视化能力，以及无人机 OSD 坐标字段的真飞确认。

三、关键缺口详解

3.1 缺口一：弹窗实时标框叠加（最核心，明天验证必缺）

当前架构：检测在 straw-engine 后端抽帧完成（cv2 拉 FLV → Detector → 得 bbox → save_evidence 存图）。弹窗（DronePopupWindow）只是前端单独再拉一路 HLS 播放，两个画面是独立的，弹窗画面看不到检测框。

要满足"弹窗画面里实时显示标框"，有两条技术路线：

路线做法评估
路线X（推荐）
后端合成推流		straw-engine 抽帧检测后，把 bbox 用 cv2 画到帧上，再重新推一路"带框流"到 ZLM（如 straw_bbox_），弹窗改播这路带框流改动小 复用现有检测帧，只需加"推流"一步；弹窗播放逻辑几乎不变
路线Y
前端叠加		后端把 bbox 通过 SSE 实时推给前端，前端在 video 上叠 canvas 按坐标画框改动大 需 SSE 同步 bbox 时间戳 + 前端坐标换算，实时对齐难

推荐路线X：最稳、明天验证最可靠。但需新增「straw-engine 检测帧→重推带框流」能力（约 0.5-1 天）。

3.2 缺口二：无人机 OSD 坐标字段（需真飞确认）

target-locator 定位需要无人机 OSD 帧里的 heading（航向）/ gimbal.yaw（云台偏航）/ gimbal.pitch（云台俯仰）/ range（激光测距）。这些字段在无人机飞行中的 OSD 帧（deviceType=1）里，今日刚修复了 ws-osd 的 deviceSn 取值 bug，但字段名与是否推送仍需真飞抓一帧确认。

风险：若无人机 OSD 帧不含这些字段（或字段名不同），坐标定位会退化到"机场坐标"（geoSource=dock），无法实现"根据无人机坐标+方向+距离"的精确定位。

六、风险与兜底

风险等级兜底
带框流推流带宽/编码开销低推流用低码率 720p、仅告警期间推，空闲不推

模型对真飞烟零检出（G1闸门已证 stage2 对远烟盲）高这是最大风险——若明天模型检不出烟，则整个验证无告警产生。需提前准备"已知烟源/低空近烟"场景，或接受"验证链路而非验证模型精度"

⚠️ 最重要的风险提醒：记忆里已有结论——v5 stage2 模型对 DJI 远烟域零检出（G1 闸门 + E1 快评 + 段2续训三次失败均证实）。明天验证若飞"远距离细微烟"，模型大概率检不出，整个实时标框链路就没有告警可展示。

建议：明天验证前，先明确验证目标是「链路贯通性」（弹窗标框→事件→坐标→乡镇→入库，用低空近烟或已知燃烧点保证有检出）还是「模型精度」（大概率无检出）。前者今天按排期做即可，后者需先解决模型（非短期可成）。

七、结论

① 事件生成后端链路（检测/坐标/乡镇/图像/置信度/入库/人工确认）已基本就绪，今天只差「弹窗实时标框」这一个前端可视化缺口；
② 建议今天按 T1-T3 落地「带框流」方案，保证明天验证的"弹窗实时标框"门面可用；
③ 坐标精确定位依赖无人机 OSD 字段，需明天真飞确认，不确认则降级机场坐标；
④ 最大风险是模型对真飞烟零检出，建议明天用"低空近烟/已知燃烧点"保证链路有告警可验。
