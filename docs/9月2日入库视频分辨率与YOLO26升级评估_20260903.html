1. 需求与结论速览

需求：① 确认 9/2 18 点左右入库的视频分辨率是否 ≥1080P；② 评估用 YOLO26 做检测是否会有更好结果。

结论：

  • ① 是，且超出预期——9/2 18 点前后入库的 Remote-Control 批次（MinIO dock_media）：V 主摄 3840×2160 (4K)、S 广角 1920×1080、T 热成像 1280×1024，全部 ≥1080P（HEVC、高码率 8~45 Mbps）。
  • ② YOLO26 值得换，但姿势很关键——同参数级 YOLO26m 全面 ≥ YOLO11m，且官方明确针对"航拍远景小目标"设计了 STAL/ProgLoss 机制，与本项目 30~130px 远烟场景高度契合；但已下载的 yolo26n 参数仅现役 YOLO11m 的 1/8，直接换 n 大概率倒退。真正瓶颈排序是「源帧分辨率 > 输入 imgsz > 骨干模型」，换 YOLO26 应与"源流提到 1080P"配套做 A/B 实验。

4. 实证二：YOLO26 官方定位与对比数据

YOLO26 = Ultralytics 2026-01-14 官方发布（标语 "Built End-to-End. Built for Edge."），核心变化：

  • 端到端 NMS-Free：NMS 内建进模型，推理链路少一步后处理，导出更顺（ONNX/TensorRT）
  • 去除 DFL：box 回归简化，边端硬件兼容性更好
  • STAL（Small-Target-Aware Label Assignment）+ ProgLoss（渐进损失）：针对小目标的正样本分配与训练节奏优化——官方明示受益场景含 distant vehicles in aerial imagery（航拍远景小目标）
  • MuSGD 优化器：SGD + Muon 混合，收敛更快、超参更稳
  • CPU 推理快 31~43%（ONNX Runtime）

5. 评估：YOLO26 会更好吗？——分三层拆解

5.1 精度瓶颈排序（本项目实测依据）

瓶颈现状可提升空间依据
① 源帧分辨率直播抽帧 720p~1080p（档位不定）最大：720p→1080p 像素 ×2.259/2 实验：抽帧像素翻倍 → conf +62%（模拟）
② 输入 imgsz1280（训练/生产一致）中：可试 1536，显存/时延成本↑v5 以 1280 收敛，小目标受益
③ 骨干模型YOLO11m@1280（v5 stage2）中：同量级换 YOLO26m +1.6 COCO + STAL 小目标机制官方 benchmark + 架构机制

5.2 分模型评估

  • yolo26n（已下载）：2.4M 参数 = 现役 YOLO11m（20.1M）的 1/8。即使 COCO n 级微升 + STAL，容量差距下对远烟小目标几乎必然倒退。yolo26n 适合 CPU/边缘高帧率场景，不适合本项目（3090 GPU 不缺算力）。不建议作为升级目标。
  • yolo26m（推荐实验）：与 YOLO11m 同参数量级（20.4M vs 20.1M），COCO 领先 +1.6，且 STAL/ProgLoss 正是为"小目标难样本"设计 → 理论上有较大概率在本数据上 ≥ v5 stage2，但需受控实验验证（模型架构收益 ≠ 必然转化，此前 v3→v4 有域差翻车先例）。
  • yolo26l/x：精度更高但训练/推理成本↑；本项目真烟正样本稀缺（百级），大模型过拟合风险大，暂不优先。

5.3 工程适配成本（常被忽略）

  • 生产 detector.py 现按 format='yolo'（[1,4+C,N] 列式 + 手写 NMS）解析；YOLO26 端到端导出的输出格式不同（NMS-free，近似 [1,N,6] 行式）→ 需新增解析分支或导出时 nms=False 保留列式结构（推荐后者，改动最小）。
  • 推理时延：YOLO26m@1280 在 3090 上与现役同量级，不影响 2s 抽帧节奏；Confirmer/告警/上报链路无需改动。
  • 训练：同 v5 数据/同 imgsz/同 conf 口径跑 val → 与 stage2 基线对比（mAP50 + 52 真烟难例召回 + fire FP 73 误报率）。

6. 推荐方案（分期）

P0 · 源流分辨率固定 1080P（先决条件，成本最低收益最大）
承接 9/2 已评估的司空2 码流档位方案（setLiveVideoQuality HIGH_DEFINITION≈1080p）+ ffprobe 验证
  • 当前直播流档位不恒定（720p/1080p 混见）→ 先固定高清档，确保检测输入像素量翻倍（本报告实证：素材端确有 4K/1080P 能力，卡点在传输档位而非采集）
  • ⚠️ 存储红线前置：1080p 码率≈2×，若同时开录像归档，须先确认 8TB 盘迁移/清理进度（记忆：剩 ~280G、日增 ~20G）
P1 · YOLO26m 受控 A/B 实验（约 2~3h GPU + 0.5d 评估）
严格对照，避免 v3/v4 式"模型换了个寂寞"
  • 同数据集（v5_train_v5 s2 划分）同 imgsz 1280：YOLO26m 从头/接力训练 vs v5 stage2 基线
  • 验收口径：val mAP50 ≥ 0.21（基线）且 52 真烟难例召回不降、fire FP 不增 → 达标才进入部署评估
  • 导出 nms=False ONNX 保持列式输出（复用现有 detector.py 分支）
P2 · 高分辨率真域样本回流（中期数据战略）
把 4K/1080P 归档变成训练资产——分辨率红利的真正兑现点
  • 从 dock_media 4K V 通道抽帧（MinIO http Range 抽帧 0.2s/张 已打通）→ VLM 预筛 → 人工整框 → 作为 v6 训练集（当前 v5 全量真烟样本来自 720p 抽帧，存在像素天花板）
  • 与 9/2 已识别的 v5.6 决策树（伪 GT 修复 / patience / 域失忆补强）合并排期

7. 风险与回滚

风险等级缓解
YOLO26m 换骨干预期不达基线（架构收益 ≠ 必然转化）中A/B 实验以 val 硬指标 gate；不达标则维持 v5 stage2（现役）不部署
P0 高清档位触发存储增长中只开直播高清、录像归档暂缓；存储迁移（8TB 转精简/扩容）优先推进
YOLO26 端到端输出与手写 NMS 逻辑不兼容低导出 nms=False 保留列式输出；或新增 e2e 解析分支（detector.py 已具备 rtdetr 行式解析先例）
真烟正样本稀缺限制大模型训练低P2 数据回流持续补强；实验用接力微调（v5 stage2 → yolo26m）控风险

回滚：模型切换 = config.json 一行 + onnx 文件替换 + detector.py 分支，旧 onnx 已留档（stage2/weights/best.onnx），回滚分钟级；DB 与前端零改动。

决策点选项建议
