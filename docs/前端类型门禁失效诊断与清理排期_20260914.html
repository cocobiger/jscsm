四、门禁方案对比（怎么装门）

方案做法优点缺点评估
A. 本地发布前置 package.json 加 "verify": "tsc --noEmit && vite build"；发版统一走 npm run verify 后再 scp（可再包一层发布脚本强制） 与真实发布链路一致；10 秒成本；不依赖网络/CI 靠流程自觉（脚本化后可硬化） 推荐·必做
B. CI 门禁（已存在） 保留现有 typecheck job；顺手核验它到底有没有在跑、是不是早就红了 零新增成本；能拦“推送/合并” 不在发布链路上；且本地 225 文件未提交、无远端跟踪 → 现状等于没生效 保留 + 核验
C. 增量门禁 只对改动文件跑类型检查（lint-staged 类方案） 快 跨文件类型影响会漏；配置与维护成本高 不建议
推荐：A + B 双层——本地 verify 做硬前置（真正拦住生产发布），CI 做兜底（拦住合并）。可选加 .git/hooks/pre-push 一行 npm run typecheck 做双保险。

五、落地步骤（可直接照做）

P0 · 清零 15 个错误（含 3 处真 bug）

  1. 改 5 个文件（6 个修复点，约 20~25 行）：StrawLivePage.tsx、TunePage.tsx、droneLive.ts、ServerReviewPage.tsx、BoundaryManagePage.tsx
  2. npx tsc --noEmit → 期望 0 错误（这是唯一的通过标准）
  3. npm run build → scp 前先备份线上 index.html + assets（沿用既有发版铁律：先备份再 scp）
  4. 部署 + 核验：新 bundle md5（磁盘==远端）+ index.html/assets 逐个 HTTP 200
  5. 页面抽查：秸秆监控 → 实时/链路全景（Worker/CPU/内存/告警数值）、算法调参页（评估集显示）、复检详情（有坐标时的 GPS 行）

P1 · 装门（把类型检查接进发布）

// package.json
"scripts": {
  "typecheck": "tsc --noEmit",
  "build": "vite build",
  "verify": "tsc --noEmit && vite build"   // ← 新增：发版前置
}

发版动作统一为：npm run verify → 备份 → scp → 重启/核验。可选：pre-push 钩子跑 npm run typecheck。

P2 · 核验与治本

  • 核验 CI 真实状态：确认 typecheck job 是否在跑、master 是否已红（本地无 git 远端跟踪，需在 GitHub 侧或推送一次后确认）
  • 契约漂移治本：15 个错误中 11 个来自“后端已改字段、前端类型没跟”。建议把前端侧接口类型集中到 src/app/lib/api-types.ts 单一出处，并在关键接口（stream-status / straw-engine status / snapshot / review list）加开发期运行时字段校验（仅 dev 告警，不阻断）
  • 巡检：每次发版前 npm run verify 即为常态巡检，无需额外机制

P3（可选/暂缓，需单独拍板）

  • 打开 noUnusedLocals / noUnusedParameters（会出现新一批告警，需评估）
  • 225 个未提交文件的版本治理：这是一个独立且更重要的风险（HEAD 停在 9/3，9/4 起全部改动无版本保护，一旦误删/覆盖无法回滚到某个中间态）——建议按业务分批提交，不要一次性全提交，需要你单独授权
