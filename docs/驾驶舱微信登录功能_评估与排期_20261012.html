3 · 关键技术发现（这 4 条决定方案怎么选）

3.1 🔴 登录判据有坑 —— 必须先实测定标（否则 F1/F3 必然失效）

读 wechat_bot_server.py 得到的事实：

  • _refresh_cache()（唯一填充 STATE['driver'|'sessions'|'wechat_version'] 的地方） 全文件只有 1 处调用：line 803，在发送成功之后。
  • /health 里 driver 的取值是 STATE['driver'] or DRIVER_NAME， 而 DRIVER_NAME 只在 load_driver() 成功后才有值。
  • load_driver() 判定成功的条件是 if info:，但 get_self_info() 永远返回一个 dict（不会是 None/空） —— 即"取不到信息"时它返回 {"username": wxid, "nick_name": "", "remark": ""}。 ⇒ driver 非空并不等于"已登录"，只等于"WeChatDB() 构造成功"。
结论：现阶段不能凭 /health 判断登录。必须在 VM 上跑一次 对照实验（未登录态 vs 已登录态各采集一遍 WeChatDB() / get_self_info() / get_sessions() / get_groups() / WTSGetActiveConsoleSessionId 与窗口几何）， 找出一个稳定可判的信号，再写进桥和守护。

💡 已有辅助信号可交叉验证：登录窗口几何实测稳定为 296×388，登录后主窗口明显更大 —— wx_front.py 已经在报窗口 rect，可作为"备用判据"，但不建议单用（窗口可能被用户手动缩放）。

3.2 ✅ 能列出「全部群」，不限于最近会话（F5 的关键）

从 VM 上取回 wechatauto/db.py（146 KB）后确认以下 API 存在：

def get_self_info(self) -> dict                       # 当前登录账号 wxid / nick_name
def get_sessions(self, limit: int = 100) -> List[dict]  # 会话列表（来自 session.db）
def search_contact(self, keyword: str) -> List[dict]    # 按昵称/备注/微信号搜联系人
def get_groups(self) -> List[dict]                       # ★ 列出所有群聊
                                                         #   username / name / owner / member_count / members
def group_name_to_id(self, name: str) -> Optional[str]   # 群名 → xxx@chatroom
get_groups() 直接查 chat_room + chatroom_member 表， 不吃"最近会话"这个限制 ⇒ 前端下拉里能出现全部群。
⚠️ 但发送侧仍需验证：桥的 resolve_group() 是在"最近会话"里按关键字找的， quick_send(who=...) 走的是微信侧栏/搜索匹配。所以"列得出来"≠"发得出去"， 对"从未打开过的群"必须实测（见排期 T15）。

3.3 权限：后端读不到二维码（必须先调）

对象现状目标
后端进程身份jsc-backend.service → User=jsc / WorkingDirectory=/data/HBJSC/backend不变
/data/HBJSC/wxb_qr/drwx------ root root ⇒ jsc 完全读不到drwxrws--- root:jsc（2770）
latest.png-rw------- root root-rw-r----- root:jsc（640）
刷新请求标志文件—目录组可写 ⇒ jsc 可创建 reset.request

采用 setgid（2）：目录下新建文件的组自动继承 jsc，避免守护每次写文件后权限又变回去。

3.4 二维码 = 登录令牌 ⇒ 安全边界必须写死

  • 二维码等价于该微信号的登录凭据，谁拿到谁就能登。
  • ⇒ 相关接口一律 adminOnly，绝不加进 PUBLIC_PATHS/PREFIX_PATHS。
  • ⇒ 响应头必须 Cache-Control: no-store, no-cache, must-revalidate + Pragma: no-cache，禁掉浏览器/中间代理缓存。
  • ⇒ 不落任何"推给用户看"的日志（PushLogPage 之类），也不进 git。
  • ⇒ 建议用小号登录（README 已有此建议）。

4 · 方案对比：3 个关键选择

4.1 二维码怎么送到浏览器？

方案做法评价
A 后端直接读本地文件 推荐 后端（就在 226 上）GET /api/wechat/qr → 读 /data/HBJSC/wxb_qr/latest.png → 流式返回 ✅ 零新增依赖、零额外网络跳、文件系统天然是最新态
⚠️ 需调目录权限（§3.3）
B 桥新增 /qr 桥在 Windows 上自己截图并返回 PNG ❌ 桥在 Windows、二维码在 Linux，桥拿不到那个文件；要桥自己截图就重复实现守护已有的逻辑（还多一份要维护的静默错图风险）
C nginx 直接静态暴露 把 wxb_qr/ 挂到 nginx 下 ❌ 安全不可接受：等于把登录令牌放到公网静态路径上，绕过 adminOnly 鉴权

4.2 「手动刷新」怎么触发重置？

方案做法评价
A 标志文件 推荐 后端写 wxb_qr/reset.request → 守护轮询到就执行重置并删掉标志；接口立即返回 202 {status:'resetting'}，前端轮询状态 ✅ 重置权只归守护一家（避免两处同时 taskkill 打架）
✅ 后端（jsc）不需要 root、不需要 SSH 凭据
⚠️ 最坏延迟 = 守护循环间隔 30 s + 重置 25 s ≈ 55 s（可接受，UI 有进度态）
B 后端 spawn wx_qr_reset.sh 后端 child_process.spawn 脱离执行脚本 ⚠️ 脚本要读 /root/.wxbridge.env + 调 wmiexec.py ⇒ 后端得跑成 root（降安全）或改权限；且与守护可能并发 taskkill
C 桥自管 /relaunch 桥暴露"自杀+重启微信"端点，后端代理 ⚠️ 桥自杀式端点有历史教训（会把端口交接/自愈脚本搅在一起）；且它看不见二维码文件，无法确认"新码出来了"

4.3 「推送对象」怎么存？

方案做法评价
A 复用 area_responsibility.webhook（只改交互） 推荐 库里仍存 URL（http://172.16.8.16:18888/send?group=<群名>），前端把"手填 URL"换成"下拉选会话"，并保留"自定义 URL"兜底 ✅ 后端推送逻辑一行都不用改（findResponsibility → sendWechatPush 原样跑）
✅ 向后兼容：已配的企微 webhook 仍能用
✅ 风险最小、可独立回滚
B 新建 wechat_target 表 + 映射 独立存"会话名 → 对象"，再关联到镇街 ⚠️ 引入第二个真源，与 area_responsibility.webhook 可能不一致；违背"口径唯一真源"的既有教训
C 全局默认对象 + 逐行覆盖 选一个全局默认群，个别镇街单独覆盖 ✅ 实际运维更省事（51 个镇街不用逐个选）
⇒ 建议作为 A 的增值项（kv_config 里存一个默认对象，findResponsibility 取不到时回落）

推荐组合：A + C（逐行为主、全局默认兜底）。

8 · 冲突排查（逐条对照既有约束）

风险点排查结论
TDZ 崩进程新模块的 require 必须放在 adminOnly 定义之后（index.js:2494）。这是 const TDZ 陷阱，前面引用会 ReferenceError 直接崩后端。已列入 T11 验收项。
不得动研判闸门本需求完全不碰 judgeWarning / isGateExemptWarning / queryWarningsAggregated；只"读会话列表 + 改 webhook 值"，推送链路代码零改动。
两条推送链路混淆本需求只服务链路 A（秸秆）；不涉及链路 B 的 smart_push_history / cyzx_report_log。
前端类型门禁发布前必跑 npm run verify；契约唯一出处 src/app/lib/api-types.ts（T12 先行，避免类型漂移）。
与保活守护争夺"重置权"采用标志文件（§4.2 A）⇒ 重置动作仍只由守护执行，不会出现两处同时 taskkill。
轮询压力打爆桥/login-state 走 DB 解密，重。必须有负缓存节流 + 前端 5 s 轮询 + 后端 3 s 结果缓存（两层）。否则每次轮询都跑一遍驱动探测。
UI 并发安全只读 DB 的端点不进 WORKER_LOCK；任何"点微信窗口"的操作必须进锁。设计上把"读 DB"与"动 UI"严格分开。
二维码被缓存/泄露no-store + adminOnly + 不进 PUBLIC_PATHS + 不写操作日志（§3.4）。
后端用户读不到文件T3 先行；setgid 保证守护后续写入仍继承 jsc 组。
构建产物内嵌凭据前端只拿"会话名"，不该出现任何 bridge 端口之外的东西；上线前跑一次既有 skill build-artifact-credential-leak-audit。
