2 · 需求拆解：每一项「该不该做、怎么做」

2.1 GPU 驱动 —— 必须做

为什么必须：训练离不开 CUDA；且引擎侧 onnxruntime 目前只有 CPU provider —— 历史实测 GPU 上 2×2 切片推理 134 ms，CPU 会慢一个数量级，实时性直接不达标。
怎么做（按 Secure Boot 分两条路）： 
# 路线 A（推荐）：用 Ubuntu「预签名」模块包，Secure Boot 保持开启
#   ⚠️ 必须选「由 linux-modules-nvidia-* 提供」的驱动版本（= Canonical 已签名）
#   实测本内核 5.15.0-194-generic 有预签名模块的：580 / 595 / 610（含 -server / -open）
#   ❌ 545 只有 nvidia-dkms-545（现场编译、无签名）→ Secure Boot 开启时加载失败
apt install nvidia-driver-580                 # 服务器/无人值守场景也可用 nvidia-driver-580-server
apt install nvidia-dkms-580                   # 不需要

# 路线 B：先关 Secure Boot（在 ESXi 的 VM 设置里取消 EFI secure boot），再用 DKMS
apt install nvidia-driver-545 dkms            # 关掉 SB 后 DKMS 才能加载
怎么判断该选哪个版本（一条命令）： 
ubuntu-drivers list | grep nvidia
#   nvidia-driver-580-open  (kernel modules provided by linux-modules-nvidia-580-open-generic)  ← ✅ 预签名
#   nvidia-driver-545       (kernel modules provided by nvidia-dkms-545)                        ← ❌ 无签名
# 「provided by linux-modules-nvidia-*」= 可保留 Secure Boot；「provided by nvidia-dkms-*」= 必须先关 SB
路线 A / B 对比（一次说清）
维度A · 预签名包（不动 Secure Boot）B · 关掉 Secure Boot + DKMS
做什么apt install nvidia-driver-580（模块由 linux-modules-nvidia-580-generic 提供）ESXi 里 VM 设置取消 Secure Boot → apt install nvidia-driver-545 dkms
为什么能加载模块已被 Canonical 签名，且该密钥在 UEFI 信任库里 → 固件放行Secure Boot 关了 → 不再校验签名，任何 .ko 都能加载
优点不动固件设置；不用进 ESXi 改配置；安全等级不降一劳永逸：以后任何 DKMS 模块（不只 nvidia）都能加载，不受内核升级影响
缺点 / 风险① 必须选有预签名模块的版本（本机 545 就没有，只有 580/595/610）；② 内核升级后要确保同步装上匹配的 linux-modules-nvidia-* 包，否则重启后驱动失效① 降低该 VM 的启动安全（可加载未签名内核模块）；② 需要在 ESXi 侧操作（改 VM 设置 + 关机重启）；③ 这是个"永久改配置"的动作
本机可行性✅ 可行（实测 linux-modules-nvidia-580-5.15.0-194-generic = 5.15.0-194.204+1，正好匹配当前内核）✅ 可行（但需你在 ESXi 点几下）
推荐先走 A（本机已验证可行，不用动 ESXi）；仅当 A 出问题（如某个 580 变体仍拉 DKMS）再退 B
三个风险点：① Secure Boot 拒签 → modprobe nvidia 失败；② 需重启（服务中断约 2 分钟）； ③ PCI 直通下驱动初始化失败（RmInitAdapter failed）虽少见但要留后路（可 apt purge 回滚 + 退回 CPU 推理）。
驱动版本建议：nvidia-driver-580（或 595/610）—— 不选 545（只有 DKMS，与 Secure Boot 冲突）； 不必装完整 CUDA Toolkit（PyTorch 轮子自带 CUDA 运行时）。

2.2 训练依赖（torch + ultralytics）—— 简单但要避坑

🔴 实测踩坑预警：直接 pip download torch 拿到的是 CPU 轮子（torch-2.14.0+cpu 一类）。 必须显式指定 CUDA index，否则装完发现 torch.cuda.is_available()==False，训练只能跑 CPU。 
python3 -m venv /data/HBJSC/train-venv                  # ★ 独立 venv，别动在跑的 straw-engine
/data/HBJSC/train-venv/bin/pip install -U pip
/data/HBJSC/train-venv/bin/pip install torch torchvision \
    --index-url https://download.pytorch.org/whl/cu124        # ← 关键
/data/HBJSC/train-venv/bin/pip install ultralytics opencv-python-headless numpy
/data/HBJSC/train-venv/bin/python -c "import torch;print(torch.cuda.is_available(), torch.version.cuda)"   # 门禁：必须 True

为什么用独立 venv：训练要 ultralytics（会拉一堆依赖），混进生产引擎的 venv 有把推理环境搞坏的先例风险。引擎侧若要用 GPU，单独把 onnxruntime 换成 onnxruntime-gpu 并重启即可。

2.3 自动标注的 VLM —— 要，但用途必须限定

先看历史结论（已论证，别重走）
❌ 「VLM 文字提示 → YOLO 画框」技术错位、不可行：普通 YOLO 是"图像→框"端到端检测器，不接受文字提示； VLM 的语义描述无法转成精确像素框。
❌ VLM 直接出框：带 grounding 的 VLM 定位精度差（远烟小目标更差）、秒级推理不实时。
✅ VLM 的正解是「离线预筛 + 难负挖掘」——项目已在跑（v54 治理流程）：VLM 判"有烟/无烟" → 挑候选帧交人工框； 同时把「模型报了但 VLM 判无烟」的样本复用为难负（hard negative）。
本次部署（HF 不通，走国内源）： 
# 官方 release 装到数据盘（历史方案已评估过：/video/ollama_install，不动系统盘）
curl -fsSL https://ollama.com/install.sh | OLLAMA_INSTALL_DIR=/video/ollama_install sh   # 或下载 release 手工解压
export OLLAMA_MODELS=/video/ollama/models
ollama serve &                                          # systemd 独立服务
ollama pull qwen2.5vl:7b                                # registry 可达；HF 不可达无妨
ollama run qwen2.5vl:7b "这张图里有烟吗？只回答有/无"
为什么选 Qwen2.5-VL-7B：历史用的就是它（qwen2.5vl:7b），脚本与提示词已固化； 7B 约需 6–8 GB 显存，与引擎的 ~5.5 GB 共存于 24 GB 之内，策略是随用启停（预筛时起、检测优先时停）。
不首推 vLLM：吞吐更高，但要编译 flash-attn（需 nvcc + 长编译 + 易失败），先把链路跑通再考虑升级。

2.4 抽帧数据源 —— 被忽略的阻塞项

对策（推荐）：绕开 MinIO，直录即抽
