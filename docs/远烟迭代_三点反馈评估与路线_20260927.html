根因定性：这是「尺度缺口」，不是阈值问题、也不是换结构能解决的。
现网训练集 1041 个框里，<40px 的只有 18 个（1.7%），下 5% 分位是 54px。 也就是说模型从未见过"远方轻烟"长什么样。

3.1 我的原判断错在哪

我此前的约束是「6 路流 × interval 2s ＝ 3 帧/s × 0.34s ≈ 1.02 s/s ≈ 单卡满载，无余量」。 这是把 6 路同时在飞的最坏情形当成了常态。按你的反馈（每天 ≤5 次飞行、大部分时间单机场起飞）， 真实负载是 单路 0.5 帧/s，预算 2000ms/frame。

3.2 这个纠正解锁了什么

能力说明代价
ROI 放大 / 2×2 切片 把"远处"所在的天空带裁出来单独放大再推理，等效像素尺寸立刻提升 2–4 倍：<40px 变成 80–160px（模型最擅长的档）。复用现网权重、零训练，可先量出"纯结构红利"的天花板。 134 ms（6.7%）
提高 imgsz 1920 → 2560。 61 ms（3.0%）
interval 2s → 1s 这是最有价值的一项：采样率翻倍 ⇒ 帧间位移更小、运动信号更连续 ⇒ 时序判别（长时中值背景 + 帧差）真正可行。而时序才是把"缓慢上升扩散的轻烟"与"整体漂移、形态稳定的碎云"分开的唯一正解（单帧信息量不够）。 翻倍帧数，仍充裕
两条必须写进设计的约束
  1. 多机重叠要降级。项目里已观测到"多机先后起飞、后者中断前者约 14 秒"。重活路径只在活跃流 ≤2 路时开启，超出则回退廉价路径——绝不能因为加了重活把实时链路拖垮。
  2. 先挖 last_ms 的 290ms 开销。main.py:400 的 last_ms 量的是整个 predict() 墙钟（含 letterbox 预处理 + NMS），纯推理只有 50ms。 这 290ms 的差额比改模型更容易拿，且直接扩大所有后续方案的预算。建议 P0 先做这一项。

4. 反馈②：mosaic 评估

4.1 先澄清一个我自己的误判

我原本怀疑：当前 close_mosaic=50 而 epochs=30，会不会一开 mosaic 就被立刻关掉、白跑一轮。查了源码——不成立：

# ultralytics/engine/trainer.py:459
if epoch == (self.epochs - self.args.close_mosaic):
    self._close_dataloader_mosaic()
    self.train_loader.reset()

# 当前参数：epochs=30, close_mosaic=50  →  30 - 50 = -20
# epoch 只会走 0..29 → 【永远不等于 -20】→ 永不触发关闭
# ⇒ 设置 mosaic=1.0 后会全程生效，不存在"白开"问题
结论：mosaic 可以直接开，不需要为了它改 epochs。
但有一个真实的坑要注意：trainer.py:1085 的 resume 分支是 if start_epoch > (self.epochs - self.args.close_mosaic) → > -20 恒真 ⇒ 一旦用 resume= 续训，mosaic 会被立刻关掉。
（本项目 stage9 用的是 model=stage3_0909/weights/best.pt 迁移学习，不是 resume，所以此前未受影响——但下次要小心。）

4.2 为什么"单靠 mosaic 不够"

mosaic 把 4 张图拼成一张再整体缩放，效果是把已有目标按比例缩小（140px 的烟 → 70px 的烟）。 它买到的是尺度不变性，但买不到"远方"的另一半物理成因：

"远方轻烟"的特征mosaic 能造吗说明
尺度变小能拼图后整体缩小，等效目标边长减半
大气衰减（对比度↓、偏蓝灰、细节丢失）不能缩小后的烟仍然对比度很高、边缘清晰，与真实远烟的"发灰、发虚"差得远 —— 这是最容易让模型在实飞时失效的差异
同尺度的真实难负（天空里的小块碎云）不能mosaic 造出的"小云"只是被缩小的云，纹理统计不真实；这档难负必须真实采集/裁切
固定机位几何先验反而破坏拼图会造出"不可能的场景"（烟柱被接缝切断、村庄紧邻随机田地）→ 对固定机位域是负作用，建议用较低概率（0.5 起）做 A/B

4.3 建议做法（三件套，缺一不可）

  1. 开 mosaic：mosaic=1.0（固定机位域建议从 0.5 起做 A/B）；把 close_mosaic 改成合理值（如 5，让最后几轮用真实几何收敛——你的机位是固定的，几何先验很值钱）。
  2. 配套"大气衰减"离线仿真：对正样本批量生成退化版本（降对比度 + 轻微蓝灰偏移 + 降饱和 + 轻模糊），还原真远处的散射效果。这是 mosaic 补不上的那一半。
  3. 配真实小尺度难负：从既有 v5_hardneg/云彩（487 图）与 day_0911（2303 张未标注白天图）的天空区裁取小块云。

5. 反馈③：屏蔽画面上方 10% 的评估

5.1 实测支持你的思路

真实机场流的 767 个框里，落在画面上方 10% 的只有 8 个（1.04%）； 已人工复核的 258 个框里是 5 个（1.94%）；真实告警帧 136 框里是 1 个（0.74%）。
⇒ 屏蔽上方 10% 的代价 ≈ 漏 1~2%。思路成立。
但不要超过 10%：实测上方 20% 就要掉 7.7%（真实告警组更高达 14.7%），上方 30% 掉 12.9%。 10% 是可接受的上限，20% 以上风险显著。

5.2 画面示意（真实分布 + 两个先验）

5.3 但固定百分比有 3 个隐患，实现方式必须改

隐患实测依据后果
① 相机角度／分辨率不恒定 证据帧有 8 种分辨率（1440×1080、1280×720、960×720、2968×1732、2560×1329…）； 且真实告警组里 22% 的框落在 y 0.8~1.0（贴底） —— 那是舱内/俯视帧。 俯视帧的"上方 10%"根本不是天空而是机库盖子／地面，固定百分比直接失效。
② "接地"比"高度"更本质 秸秆焚烧的烟必然源于地面；实测真实烟底边中位 y=0.537，不会孤零零悬在顶部。 用"是否与地表连通/近接地"作判据，能同时解掉"云（悬空、四周被天空包围）vs 烟（自地表升起）"， 而且完全不受相机角度影响。
③ 动态天际线是可行的 已查证：gimbalPitch / gimbalYaw 在 dji-openapi/lib/telemetry.js:57-58 已能取到 （payloadObj.gimbalPitch 或 data.gimbal.gimbal_pitch）； target-locator.js 已写明约定（pitch：水平 0°、向下为正）。 用 云台 pitch + 相机垂直 FOV 即可算出天际线 y；俯视时 y_horizon < 0 ⇒ 画面无天空 ⇒ 自动禁用屏蔽。
现状 straw-engine 目前完全没消费 pitch（只用 droneInDock），需在"遥测 → 引擎"之间加一条字段。

5.4 建议落地形态（分级推进，不要一刀切禁止）

级别做法成本 / 门禁
L0
立即可做		 把"画面上方 10%"作为后处理规则：该区内命中的框不推送、不计告警， 但落库为 source='low'。 零训练、可回滚。
附带收益：把屏蔽区变成自动难负样本矿——后续挖"天空里的小云"直接从库里取。

L2 把"接地先验 + 天际线距离"作为二级复核特征，与时序判别一起进复核器。 与 P2 的时序复核器合并实现。
