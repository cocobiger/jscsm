秸秆焚烧「检测结果 + 复检页」需求评估与排期

需求评估 2026-08-30 关联：秸秆焚烧监控模块 · straw-engine v5 · 智治推送

一、需求理解

业务背景：秸秆焚烧告警由 AI 引擎自动推送微信群（街道办处置）或触发无人机喊话。AI 判定存在误报风险，而推送结果直接驱动街道办出动，必须有人工复检环节把关——这正是「告警分流」业务规则（有人→喊话 / 无人→街道办）落地前缺失的一环。

一句话定位：在「AI 检测 → 微信推送」链路上加装人工复检闸门，让每条推送有据可查、可纠正、可回流训练。

三、差距分析：三个核心缺口

缺口 ①：推送无人工把关（最核心，业务痛点）

现状：/api/straw-alert 入库后 setImmediate 立即推送微信群，人工复检滞后甚至缺失。误报一旦推送，街道办白跑一趟，推送权威性受损。

  • 无「复检通过才推送」的前置审核模式；
  • 已推送告警复检为误报后，无法撤回/更正推送结论（推送日志与复检结论未打通）。

缺口 ②：检测结果视图不完整、两处割裂

  • 告警工作台（StrawReviewBoard）只展示已推送的告警（warnings 表），看不到未推送的检测记录（低置信度、house 排除类等）；
  • 全量检测（straw_detections）在管理后台复检页，但不显示推送状态——「这条检测到底推没推微信」无从知晓；
  • 两处数据源互不相通，复核结论各记各的。

缺口 ③：复检页产品化不足

  • 无「秸秆业务视角」的统一复检工作台（值班员关心：今天哪些待复检、哪些已推送、误报率多少）；
  • 复核人硬编码 'admin'，未绑定登录用户（审计缺失）；
  • 缺少批量快捷复核（键盘流操作），大批量复检效率低。

现状：第 5 步缺失，检测直接跳推送（4 → 6）。

目标双模式（可配置开关，见排期第 3 批）：

  • 后置纠正模式（默认）：先推后检——推送后值班员复检，误报标记+更正推送结论，保证及时性；
  • 前置审核模式：先检后推——高置信度（如 conf≥0.7 / level≥3）才直推，低置信度进复检队列，通过后才推送。

五、方案设计（三个交付物）

① 检测结果页（统一视图）

  • 以 straw_detections 为主表，关联 warnings 推送状态（未推送/已推送/推送时间/责任单位），形成「全量检测 + 推送 + 复检」三合一视图；
  • 筛选：时间范围、类别、置信度区间、推送状态、复检状态；缩略图网格 + 列表两种模式；
  • 入口：秸秆焚烧监控页新增「检测结果」页签（与现有 7 个页签并列）。

② 复检工作台（复检页）

  • 待复检队列（默认按时间倒序，支持按推送状态过滤——优先复检「已推送」项）；
  • 快速连续复核：单键判定（1=真警 / 2=误报 / 3=漏报 / U=撤销），自动进下一条；
  • 保留现有画框补标（漏报补标）、批量改类能力，复核人绑定登录用户；
  • 顶部统计条：待复检数 / 已推送未复检数 / 今日误报率。

③ 推送联动闭环（核心业务价值）

  • 审核模式开关（kv_config：straw_review_gate = off(现状) / post(后置纠正) / pre(前置审核)）；
  • post 模式：复检误报 → 告警标记「已更正为误报」，推送日志记录更正动作；
  • pre 模式：低置信度告警进入复检队列，通过后才触发 strawWorkflow 推送（高置信度直推）；
  • 推送日志与复检结论互链，可追溯「谁在何时复核了哪条推送」。

六、排期计划（4 批，约 5 人日）

按「看得见 → 管得了 → 推得准 → 反哺模型」递进，每批独立可上线、可回退。

第 1 批 检测结果统一视图 约 1 人日
后端：review API 增强——list 返回关联推送状态（LEFT JOIN warnings 按 frame/时间匹配），新增推送状态筛选参数。前端：秸秆页新增「检测结果」页签（列表 + 缩略图 + 筛选）。
  • 交付：/api/review/list?push_state=&…、前端检测结果页
  • 验证：全量数据核对（检测数 = 推送数 + 未推送数）
第 2 批 复检工作台产品化 约 1.5 人日
后端：submit 记录 reviewer 改为登录用户名（非硬编码）；新增「已推送未复检」优先队列接口。前端：复检页快速流操作（键盘判定/自动下一条）、顶部统计条、已推送标记高亮。
  • 交付：复检工作台 + 统计条
  • 验证：走查 30 条记录复核 + 撤销全流程
第 3 批 复检 ↔ 推送联动闭环（核心） 约 1.5 人日
后端：kv_config 审核模式开关；strawWorkflow 支持「复检通过才推」分支；复检误报 → 更正推送结论接口。前端：告警工作台展示推送更正状态；审核模式配置入口。
  • 交付：straw_review_gate 开关 + 前后置审核双模式
  • 验证：mock 告警端到端（检测→复检→推送/拦截→更正）
第 4 批 复检数据资产 约 1 人日
后端：复检统计报表 API（日/周误报率、检出率、按类别分布）。前端：复检统计面板 + 「导出重训」一键入口（复用 /api/review/export）。
  • 交付：误报率报表 + 一键导出重训
  • 验证：报表与 straw_samples 手工对账
优先级建议：第 1、2 批解决「看得见、管得了」（基础），第 3 批是用户诉求「推送结果人工复检」的核心价值，第 4 批锦上添花。若人力紧张，第 1+3 批可先行（视图 + 闸门闭环），第 2、4 批后续补。

七、风险与回滚

风险说明对策
前置审核增加推送延迟晨间焚烧高发时复检队列可能积压，影响及时性默认「后置纠正」模式；前置模式仅对 conf≥0.5 的告警启用，高置信度(≥0.7)直推
微信撤回不可靠已推送消息对方可能已读，物理撤回意义有限改为「更正推送 + 标记误报」：补发一条更正消息并记录，不物理撤回
双数据源口径不一致straw_detections 与 warnings 存在时间差/重复以 straw_detections 为主表，warnings 仅作推送事件关联；匹配键=stream_id+时间窗口
复检结论污染训练数据批量误标类别会污染重训（历史教训）批量改类仅限 smoke 场景且逐张确认；导出前展示待导样本清单

回滚方式：全部改造以 straw_review_gate 功能开关 + 独立 API 形式落地，关闭开关即恢复现状推送逻辑；后端改动前备份 config.json 与 DB（既有备份流程），前端页面独立页签不影响既有功能。

八、结论

本需求可行且必要：系统检测/告警/推送/复检基础设施已齐备，核心缺口是「推送缺人工把关 + 视图分散」两处，通过 4 批改造（约 5 人日）即可形成完整闭环。

  • 第 1-2 批：让值班员「看得见、管得了」——检测结果全量可见、复检高效可操作；
  • 第 3 批：让推送「推得准」——人工复检闸门真正介入推送链路，兑现「推送结果需人工复检」的业务诉求；
  • 第 4 批：让复检「反哺模型」——误报率可量化，复检数据自动回流重训，模型越用越准。

建议按批次推进，每批上线后小范围验证再进下一批；如认可本评估，可从第 1 批直接开工。
