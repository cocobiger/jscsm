3. 根因分层

① 上游图源切换 = 主因
9/2 19:32 起，IoTCloud 下发告警 picUrl 的 host 由 111.10.220.226:5001（nginx 静态直出，免认证）切换为 172.16.8.11:6882（认证网关）。

6882 对任意路径返回 {"code":401,"msg":"...认证失败，无法访问系统资源"} —— 且是 HTTP 200 包裹的 JSON，不是图片。后端 fetchImageBytes/proxyImage 裸转发：看到 statusCode!==200（或拿到的 200 body 非图但 sharp 处理失败）→ 502 → 前端 onError → 「暂无图片」占位。当前代理层 没有 6882 的 token/cookie 注入能力，此形态下恒 401。

② 后端代理未适配认证网关
iot-fetcher.js validatePicUrl L398-413：host 白名单放行 172.16.8.11，但代理逻辑只做「静态 host 改写」，无认证透传、无 cookie 会话、无"先试 A 源再回退 B 源"能力。
③ 测试图数据叠加放大现象
DB 实证：iotcloud 7154 条 picUrl 为 :5001（正常）+ 仅 7 条 :6882（全部是 inject/p1fix 测试图，今日 5 条 iotcloud 告警全是测试数据）。

页面 60 张失败图里，一部分是 5001 测试图已删（p1fix 系列 404）、一部分是 6882 测试形态（401）。真实历史图（5001）经代理 200 正常 → 证明代理链路本身健康，问题集中在"新图源形态"。

④ 聚合告警选图逻辑缺陷（次生风险）
store-db.js L2099：previewPicUrl = 组内首条含 picUrl 成员。

若聚合组内首条恰好是 6882 死链/测试图，整组聚合卡片的预览图一起挂；即使其余成员图正常也不会被选。今日聚合组=0 属数据巧合，真机告警一旦混入死链成员即触发。

⑤ /api/evidence 相对路径缺陷（straw 证据图）
AlertThumbnail.tsx L27-32：把一切 /api/iot-image?url= 改写为 /api/thumb?url=...；但当 picUrl 本身是相对路径 /api/evidence/... 时（straw 证据图本应直链），被错误改写成 /api/thumb?url=/api/evidence/... → validatePicUrl 对非 http(s) URL 抛 Invalid URL → 400。

4. 关键实证（支撑方案选择）

证据结论
历史真实告警 7154 条 picUrl 全为 :5001，代理实测 2005001 静态源 + 现有代理 = 健康基线
今日 6882 形态测试图（90510/90511 等）在 :5001 同路径 试拉 HIT 200两图源很可能是同一份目录的两种出口（6882 = 5001 的鉴权包壳）→ host/port 归一化可行
9/2 19:32 前后 picUrl host 突变切换是上游单方面变更，我方无感知 → 需要"图源形态变更"告警/兜底机制
今日 iotcloud 告警 5 条全为测试（inject/p1fix）当前 UI 全挂 ≠ 真实业务全挂，但 真机告警一旦产生即为 6882 形态 → 必然全挂

A

6. 落地步骤（推荐组合，分 3 批）

批 1 · 止血 前端 C（0.5 天，纯前端可独立先行）
改动文件：src/app/components/AlertThumbnail.tsx
  • onError 处理：thumb 加载失败 → 若 src 是 /api/thumb?url= 形态，重置为原 /api/iot-image?url= 重试一次；再失败才渲染「暂无图片」
  • 相对路径直链：src 以 /api/evidence/ 或非 http(s) 开头时不 rewrite，直接走原生 img（修复缺陷⑤ 400）
  • 验收口径：straw 证据图 200；502 图先占位再自动变原图重试（网络面板可见第二个请求）
批 2 · 主修 后端 B（0.5 天）
改动文件：server/iot-fetcher.js（fetchImageBytes L416 / proxyImage L476）
  • 抽取统一 resolveImageBytes(url)：先按原 URL 拉取（现状逻辑）→ 若 host:port 为 172.16.8.11:6882（或 111.10.220.226:6882）且失败/401，则改写为 :5001 同路径重试 → 仍败返回原始错误
  • 双败时 log.error 记录 [img-proxy] 6882/5001 双源均失败 url=...，便于跟踪上游是否出现"5001 无副本"的新图
  • 不改 DB、不改入库逻辑（读时适配，天然可逆）
  • 验收口径：今日 6882 形态测试图 curl 后端代理返回 200 image/*；真实 5001 历史图仍 200
批 3 · 加固 聚合选图 D + 可选长期 A
改动文件：server/store-db.js L2099；长期 A 改 server/iot-fetcher.js + env
  • previewPicUrl 选择逻辑：在组内遍历时跳过「6882 网关形态 / 已判定不可达」成员，取首个健康成员；全组无健康图则 null（前端显示占位而非裂图）
  • （可选）A：向 IoTCloud 申请 6882 认证凭据 → env IOTCLOUD_6882_TOKEN → fetch 时注入 header；凭据进 .env + .gitignore，不落库不入 git

8. 风险与回滚

风险等级缓解
上游 6882 独有新图（5001 无副本）→ B 归一化 404中双源回退设计：5001 404 → 回退 6882 原样请求；双败日志留痕，便于跟进上游
B 属"适配上游"策略，上游再变则需再适配中图源形态变更日志 + 每张失败图都留痕，后续可自动告警"新图源形态出现"
C 降级重试会多发一次原图请求（流量↑）低仅 502/400 失败路径触发，正常图不重试
A 凭据泄露 / 认证策略变更低凭据存 env + .gitignore；A 仅在凭据到位后启用

回滚：读时适配未改 DB，回滚 = git revert 后端文件 + 重 scp + restart（或前端旧 bundle 从 backups/ 还原重铺），无数据迁移负担，分钟级可逆。

9. 结论与决策点

一句话结论：故障主因是 9/2 19:32 上游 IoTCloud 将告警图源切至 172.16.8.11:6882 认证网关，后端图片代理无认证透传能力导致 401→502→前端「暂无图片」占位；5001 静态源全链路健康（历史 7154 条 + 同路径 HIT 200 实测）为归一化修复提供了直接依据。

推荐执行：批 1（前端降级 + evidence 直链）→ 批 2（后端 6882→5001 读时双源回退）→ 批 3（聚合选图加固）；长期视凭据情况补 A 认证透传。
决策点选项建议
① 是否按 批1+批2+批3 组合实施A 仅止血（批1）/ B 止血+主修（批1+2）/ C 全量三批C 全量（三件套同日闭环，互为兜底）
② 是否接受"读时双源回退"这一适配策略（不动 DB、天然可逆）接受 / 改为写时归一化（入库前改 host，DB 落 5001 地址）读时（可逆、无历史数据污染；写时留作备选）
③ 是否向 IoTCloud 申请 6882 认证凭据（支撑长期方案 A）可申请 / 暂不申请建议发起申请，到位后补 A；未到位前 B 已覆盖现状
