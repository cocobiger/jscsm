一句话结论
软件全部可重建，约 39–43 人时（5–5.5 人日，熟练单人串行；并行可压到 3–4 天）。 但 AI 能力无法"重建"——数据集与模型没有任何副本，必须重新采集与训练。
两个前置阻塞：① 司空2 网段（172.28.0.0/24）从新机不通；② 老 7TiB 数据盘无备份。

4. 阻塞项与需要确认（按优先级）

优先级事项为什么卡
P0新机是否会被继续占用 新机现在几乎是空的（系统盘 12G、/data 为 0）⇒ 抢回窗口期。一旦对方铺上业务，地址/配置/磁盘再变一次，前面所有工作重做。
P0172.28.0.0/24（司空2）为何不通 路由已走默认网关、网关 ping 通，但 4 个端口全超时 ⇒ 需网络方确认是服务不在还是ACL 不放行。不解决则 P1 的 dji-openapi 与全部视频链路无解，方案 A 的"视频直播"也拿不到。
P17/9→今天 的业务数据是否有别的副本 决定"数据损失"是 2.5 个月还是一次导出。建议排查：同事机器导出、Windows VM（172.16.8.15，仍存活）上的文件、历史邮件附件、以及本机 tmp/ 下的零散抓取。

5. 实施风险与回滚

风险应对
又把大数据写进系统盘 旧机靠独立 7T 数据盘隔离；新机是 /data(5T)。先建 /video → /data/video 软链并确认所有配置走软链路径，再动任何数据。
装 GPU 驱动导致重启/失联 PCI 直通卡在新内核上装驱动需重启；安排在可控窗口，且事先确认 22233 映射稳定、能重新登录。
还原 7/9 配置带回过期假设 7/9 的 nginx/ZLM/backend 配置里含旧 IP、旧 secret、旧凭据。逐项核对再启动，尤其：ZLM secret、司空2 凭据、MinIO 地址、iotcloud.env。
onnxruntime-gpu 与 CUDA 版本错配 → 静默回退 CPU 既有教训：手动 venv python 推理必须带 systemd 的 LD_LIBRARY_PATH。
门禁：显式打印 provider 列表，确认 CUDAExecutionProvider 在首位。
重写 main.py 与既有行为不一致 用记忆中的可观测契约做回归：/health 字段、cfm.{hits,need,status}、frame_age_s、landing_suppress、夜判阈值（亮度<25 或 19–05）。不满足不算完成。
通用回滚原则（延续既有铁律）：① 每阶段结束把配置与代码打 tar 存本机（不许只留在服务器上）； ② 改配置前先 cp 原版；③ 大数据只写 /data，不动系统盘； ④ 本次事故的直接教训——同机备份等于没备，关键产物必须有离开该主机的副本。

6. 结论

  1. 软件可重建：39–43 人时（5–5.5 人日）；最重单点是 straw-engine/app/main.py 的重写（8–12 人时）。
  2. GPU 保住了（RTX 3090 直通仍在），这是本次唯一的大运气——否则 AI 链路要换机器。
  3. AI 能力不可"重建"：数据集与模型零副本，只能重新采集+训练 ⇒ 这是关键路径，越早排期越好。
  4. 两个前置阻塞：新机归属（抢回窗口）+ 司空2 网段可达性。这两件事没结论前，P1 无法真正收尾。
  5. 方法论资产全在（协议 v1.2、标注工作台、锚点工具、验收探针、109 份评估文档、skill）——口径和经验没有丢，这比代码值钱。
