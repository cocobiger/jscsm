编制时间：2026-09-08评估方式：ZLM 码率数据排查性质：可行性 + 实现方案

一、结论摘要

需求完全可行：司空 ZLM 的源流有 bytesSpeed 字段（实时码率，字节/秒），可拿到当前直播流的实时带宽占用。

核心判断：单路 720P 直播流码率 ~0.6 MB/s（占上行 20%），单独不会占满上行；但 dock_media 录像上传（HEVC 高码率）与直播流同时时，上行可能接近/超过 3MB/s——这是网络拥堵的真实风险点。

建议实现：弹窗显示"机场上行带宽占用"（实时码率 + 占用百分比进度条 + 拥堵预警），帮助值班人员预判网络风险。

二、需求理解

在无人机直播弹窗显示当前起飞无人机所属机场的网络流量数据，监控上行带宽占用，预判是否会造成网络拥堵。机场带宽 20M（下行），上行 3MB/s（约 24Mbps）基本占满。

三、数据源分析

数据源实测说明
司空 ZLM 源流 bytesSpeed637750 字节/秒 ≈ 0.61 MB/s无人机 RTMP 推流到司空的实时上行码率（720P 直播流），核心数据源
司空源流 tracks（fps/分辨率）960x720 fps=30流的编码参数（辅助）
dock_media 录像上传HEVC 1080P/4K，准实时上传（滞后 6-9min）高码率，是上行占用的大头（飞行中实时分段上传）
OSD 遥测WebSocket，极小可忽略

关键认知：bytesSpeed 是单路流的码率，反映"这一路直播流占用的上行带宽"。但机场上行是共享的——如果同时有"直播流 + dock_media 录像上传"，总上行 = 各流码率之和。

四、带宽占用构成与拥堵风险

占用项码率（估算）占上行（3MB/s）比例
直播流（司空 mirror，720P）~0.6 MB/s/路~20%
dock_media 录像上传（HEVC 1080P）~1~3 MB/s（高码率）~33~100%
dock_media 录像上传（HEVC 4K）~3~6 MB/s（更高）~100~200%
OSD 遥测~0.01 MB/s可忽略

4.1 拥堵风险场景

场景总上行估算拥堵风险
仅 1 路直播流（无录像）~0.6 MB/s（20%）安全
1 路直播流 + 1080P 录像上传~1.6~3.6 MB/s（53~120%）接近/可能占满
1 路直播流 + 4K 录像上传~3.6~6.6 MB/s（120~220%）占满/拥堵
2 路直播流 + 录像上传更高高风险

核心结论：网络拥堵的主要风险不是直播流本身（720P 仅 0.6 MB/s），而是 dock_media 录像上传（HEVC 高码率）与直播流同时——飞行中录像实时分段上传（准实时），4K 录像 + 直播流同时上行可能直接占满 3MB/s，造成网络拥堵、直播卡顿、甚至推流中断。

五、实现方案

5.1 后端接口

GET /api/drone-events/network-status?dockSn=<机场SN> 返回： { ok: true, dockSn: "8UUXN7G00A0FDP", dockName: "环保局机场", // 实时码率（司空 bytesSpeed 汇总） liveKbps: 4900, // 直播流码率 kbps（bytesSpeed × 8 / 1000） liveMBps: 0.61, // 直播流 MB/s recording: true, // 是否有录像上传中 recordKbps: 2000, // 录像上传码率（估算/实测） totalMBps: 0.61, // 总上行占用 MB/s uplinkMBps: 3.0, // 上行带宽阈值 MB/s usagePct: 20, // 占用百分比 level: "safe" // safe(<60%) / warn(60-90%) / danger(>90%) }

5.2 前端弹窗显示

元素内容
网络流量指示条弹窗底部加"机场上行"指示条：实时码率（MB/s / Mbps）+ 占用百分比进度条
拥堵预警占用 >60% 黄色预警、>90% 红色告警（"上行接近占满，可能卡顿"）
录像上传提示如有 dock_media 录像上传中，显示"录像上传中 +X MB/s"

5.3 数据流

司空 ZLM bytesSpeed（源流码率） → 后端汇总（live + dock_media 上传估算） → 计算总上行占用 + 百分比 + 拥堵等级 → /api/drone-events/network-status → 前端弹窗轮询（2s）显示 + 预警

六、关键设计决策点

决策点选项建议
dock_media 上传码率怎么拿A. 从 MinIO 上传速率估算 B. 从司空录像文件大小/时长算 C. 固定估算值先 C（固定估算 1080P~2MB/s、4K~4MB/s），后续接 MinIO 实测
bytesSpeed 用哪个A. 司空源流（无人机推流上行）B. 我方 mirror 流（司空到我方）A 司空源流——反映机场上行占用；mirror 流是我方下行，不占机场上行
拥堵阈值上行 3MB/s按用户给定 3MB/s；预警 60%（1.8MB/s）、告警 90%（2.7MB/s）

七、工作量评估

任务说明工作量

前端弹窗流量指示实时码率 + 进度条 + 拥堵预警0.5 天
联调验证真飞时验证码率准确性 + 预警触发0.5 天

合计约 1~1.5 天。

八、结论

① 需求可行：司空 ZLM 的 bytesSpeed 提供实时码率，可监控机场上行占用；
② 核心风险是 dock_media 录像上传（HEVC 高码率）与直播流同时——4K 录像 + 直播流可能占满 3MB/s 上行，造成拥堵；
③ 建议实现：弹窗显示"机场上行带宽占用"（实时码率 + 占用百分比 + 拥堵预警），预警 60%/告警 90%；
④ 工作量约 1~1.5 天，数据源已就绪（司空 bytesSpeed），dock_media 上传先用估算值、后续接 MinIO 实测。

本报告基于 2026-09-08 ZLM 码率数据排查（司空 bytesSpeed=637750 字节/秒 ≈ 0.61 MB/s，960x720 fps=30）。核心结论：直播流本身不占满上行，dock_media 录像上传（HEVC 高码率）是网络拥堵的主要风险。
