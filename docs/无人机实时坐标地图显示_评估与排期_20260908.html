一、结论摘要

需求可行，数据源已确认存在，但需要打通一段"数据暴露"链路 + 一次真飞验证。核心结论：

① 驾驶舱电子地图已具备渲染能力（机场标记 + OSD 遥测信息窗已上线）；
② 司空系统确实推送无人机实时经纬度（OSD deviceType=1 帧，字段 latitude/longitude/height，已反编译 SDK 证实）；
③ 当前缺口：dji-openapi 的 OSD WebSocket 尚未把无人机帧暴露出来（实测 /api/telemetry/latest 只有机场帧 deviceType=0）；
④ 关键前提：无人机 OSD 帧推测仅在「飞行中」才推送（在仓时司空不推），需一次真飞确认。

三、方案对比

方案做法评估
A（推荐） 先打通链路 + 真飞验证：
① dji-openapi 暴露无人机帧（telemetry.allLatest 已按 deviceSn 去重，需确认无人机帧 key 用 childSn 不冲突）
② 后端 /api/sikong/devices 附带每机场的无人机实时坐标
③ 前端 MapView 给"飞行中"无人机单独打实时 marker
④ 真飞时验证字段与刷新频率		 稳妥 分阶段、风险可控，先验证数据再上 UI
B 直接按 latitude/longitude 假设写全链路代码，真飞时一起验证 快但赌 若字段名/推送时机与假设不符需返工

推荐 A：因唯一不确定点是"无人机 OSD 帧的推送时机与字段"，这个只能真飞验证，先做不依赖该不确定性的链路部分，把风险收敛到"最后一步真飞"。

四、落地步骤（方案 A）

步动作说明
G1dji-openapi 暴露无人机 OSD 帧确认 ws-osd 无人机帧(deviceType=1)被 record；telemetry.allLatest 按 deviceSn 去重时无人机帧不丢失；必要时 /api/telemetry/latest 增加 deviceType 区分

G4真飞验证 + 刷新频率调优一次真飞确认字段值/推送频率，调整 marker 刷新间隔（避免抖动）

五、冲突排查

潜在冲突排查结论
机场 marker vs 无人机 marker 重叠在仓时只显示机场；飞行时无人机 marker 叠加（可偏移或替换），需前端区分 droneInDock 状态
坐标偏移（GCJ-02 vs WGS-84）司空给的经纬度是 WGS-84 还是 GCJ-02 需真飞验证；MapView 已有 coord 转换工具，可复用
OSD 轮询频率当前 ws-osd 是推送式，前端应订阅而非轮询；若走 /api/sikong/devices 轮询，需控制频率（建议 3-5s）
与秸秆检测拉流的资源争用无——坐标是 OSD 遥测通道，与视频流(ZLM)独立

六、风险与回滚

风险等级回滚
无人机 OSD 帧真飞时字段名与假设不符中G1 阶段先抓一帧确认字段，不符即改 pick() 路径，不改核心逻辑
真飞时无人机坐标频繁跳动导致 marker 抖动低前端做坐标平滑/最小位移过滤
改动影响现有机场标记/OSD 信息窗低纯增量（新增无人机 marker 字段），不改机场渲染逻辑，git 可回滚
