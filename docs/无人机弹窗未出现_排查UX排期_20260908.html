—— 三峡学院无人机起飞后前端无弹窗拉流
编制时间：2026-09-08排查方式：日志 + DB + OSD + ZLM 四层交叉性质：根因定位 + UX + 排期

一、排查结论（根因）

根因：三峡学院无人机并未真正起飞，司空没有推送 LIVE_ON 直播事件，所以整条弹窗链路没有触发。

这不是代码 bug，而是"无人机状态"与"用户感知"的错位。

1.1 四层证据链（逐层排查）

层实测结论
司空 OSD（源）三峡学院 OSD：droneInDock=True（在仓）、childSn=None（无挂载无人机）无人机在仓
司空 ZLM 直播流只有 live/8UUXN8N00A0LS7（机场 dock 流），无 1581F8HGX258600A0S4G（无人机流）无无人机流
webhook 事件今天 12 条全是 FLIGHT_TASK_STATUS_CHANGE（且都是经开区），0 条 LIVE_STATUS_CHANGE无直播事件
DB / 前端drone_live_events 今天 0 条 → 无 SSE 广播 → 无弹窗链路未触发

1.2 发现的真实隐患（昨日过滤改动埋的雷）

昨天的"只拉无人机流"过滤基于错误假设：以为无人机起飞时司空只推 1581F 无人机流。但昨天历史日志证明——司空在无人机起飞后先后推两种流：

18:21:28 司空直播流出现: live/8UUXN8N00A0LS7 ← 机场 dock 流（持续存在） 18:21:43 司空直播流出现: live/1581F8HGX258600A0S4G ← 无人机流（延迟 ~15s 才出现）

风险：若无人机起飞瞬间只推 dock 流、无人机流延迟出现，则过滤规则会把 dock 流跳过，导致起飞初期弹窗"等待视频流接入"卡 15 秒甚至更久；且如果某些机型只在起飞时推 dock 流（不推无人机流），则弹窗永远无流可播。

更严重的隐患：昨天"过滤 dock 流"的需求初衷是"不要机场监控画面"，但无人机飞行时，司空推的流名取决于机场推流配置，未必是 1581F。当前过滤规则 /^1581F/ 是脆弱的硬编码，一旦流名规则变化，弹窗就会静默失效。

二、UX 评估（用户旅程痛点）

2.1 当前用户旅程

步骤现状痛点
1. 无人机起飞用户在现场/后台看到无人机离开机库—
2. 司空推直播事件依赖司空 LIVE_STATUS_CHANGE webhook若司空不推则全链路静默
3. 前端弹窗依赖 SSE 广播 + zlm-watcher 拉流拉流延迟 ~9-15s，起飞初期空白
4. 弹窗显示画面带框流/原流播放无"起飞中/准备中"状态反馈

2.2 核心 UX 痛点

#痛点严重度
1无状态反馈：无人机起飞后到画面出现前，前端无任何"已检测到起飞、正在接入视频流"的提示，用户只能干等，误以为"没反应/坏了"高
2拉流延迟黑盒：镜像接入滞后 9-15s，期间弹窗停留在"等待视频流接入…"，无倒计时/无预估，体验断裂高
3事件依赖脆弱：弹窗完全依赖司空 LIVE_STATUS_CHANGE webhook，一旦司空不推（本次就是），无任何兜底（如轮询 OSD droneInDock 变化）中
4流名硬编码：zlm-watcher 按 /^1581F/ 过滤流，流名规则变化即静默失效，且无告警中
5无诊断可见性：用户看到"没弹窗"，但没有任何界面能告诉他"无人机在仓/事件未到/流未接入"是哪一环断了中

五、结论

① 本次"没弹窗"不是代码 bug：三峡学院无人机实际在仓（OSD droneInDock=True），司空未推 LIVE_ON，链路未触发；
② 但暴露了 3 个真实隐患：拉流过滤脆弱（流名硬编码）、事件单点依赖（无 OSD 兜底）、无状态反馈（用户误以为坏了）；
③ 建议先做 P0 两项（过滤修复 + OSD 兜底），从根上提升弹窗可靠性和容错；
④ 下次真飞验证时，可先用后台/日志确认"OSD droneInDock 是否 1→0"判断无人机是否真起飞，避免误判。

本报告基于 2026-09-08 10:30 四层交叉排查（司空 OSD / 司空 ZLM / webhook 日志 / DB）。核心结论：无人机在仓未起飞，链路未触发；同时发现拉流过滤脆弱 + 事件单点依赖 + 无状态反馈三个隐患。
